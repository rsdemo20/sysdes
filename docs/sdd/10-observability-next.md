# sysdes — развитие наблюдаемости и Product/UX SLI

Статус: **Deferred — следующие итерации; не входит в MVP**. Область: измерение работы пользователя в редакторе sysdes после появления задачи полевой аналитики. Документ сохраняет определения и варианты реализации; он не требует сейчас collector, кликстрим, API, таблицы, отчётный GUI или выполнение статистических SLO на реальных сессиях.

Текущий минимальный объём технических проверок — в [09-technical-sli.md](09-technical-sli.md). Приоритет уточнения пользователя: метрики не должны заметно замедлять разработку приложения. Всё упоминание реализации, sampling, field SLO, хранения и отчётов ниже относится к будущей итерации и потребует отдельного решения о её начале.

User-centric Latency описывает технический отклик. Product/UX Metrics описывают наблюдаемое выполнение задач и дополнительные действия. Требования и критерии приёмки приложения, которое пользователь проектирует на холсте, остаются отдельными данными документа; телеметрия sysdes в них не добавляется.

Пороги `>94%` сессий плавного взаимодействия, `>90%` действий без быстрой отмены и `>87%` успешных подключений взяты из запроса пользователя. Пороговые времена — 100 ms, 3 s и 5 s. Внутрисессионное условие плавности и все остальные процентные цели ниже — **предложенные** уточнения. Строгое `>` не заменяется на `>=`.

## 1. Единицы, окно и знаменатели

- `editorSessionId` — случайный идентификатор открытого редактора в одной вкладке. Новый после logout, reload, смены аккаунта или 30 минут без пользовательского ввода и без продолжающегося жеста. Это не auth-сессия. Переключение холстов внутри вкладки не начинает новую сессию.
- `operationId` — один пользовательский intent; несколько pointer events и обновлений React не создают несколько операций. `commandId` — одна зафиксированная команда undo-истории. `taskAttemptId` — одна попытка выполнить заранее определённый сценарий.
- `interactionMode`: mouse, touchpad, keyboard, touch. Pointer и keyboard рассматриваются отдельными группами; низкое число кликов при управлении клавиатурой не объявляется улучшением mouse UX.
- `activeSessionTime` — объединение foreground-интервалов от пользовательского ввода до следующего ввода (максимум 30 секунд после последнего события) **и всего foreground-времени продолжающихся пользовательских жестов**, включая неподвижное удержание. Интервалы не перекрываются при суммировании; ожидание без ввода и без жеста не добавляет бесконечное активное время. Поэтому foreground drag time является подмножеством activeSessionTime, и доля времени не превышает 100%. Искусственный rAF/heartbeat активность пользователя не продлевает.
- Для плавности считаются только foreground-интервалы drag/pan/zoom. Idle-время между жестами и фоновые вкладки исключаются. Время удержания неподвижного блока сохраняется отдельно, чтобы оно не скрывало рывки во время движения; SLO плавности строится по интервалам с изменением положения/масштаба или ожидающим визуальным обновлением.
- Длительности считаются в одной монотонной шкале времени документа (`performance.timeOrigin` / `performance.now()` / совместимый `event.timeStamp`). Серверное время приёма не заменяет время взаимодействия.
- Основное окно SLO — скользящие 28 суток, отчёт по UTC-дням и версии приложения. Отдельно — cold load / первый выбор холста / переключение холста, тип операции, размер сцены, браузер и input mode. Релизы и определения метрик нельзя смешивать в одном сравнении без разбиения.
- Для каждой доли сохраняются **good, bad, unknown, excluded** и причина исключения. В знаменатель измеряемой доли входят good + bad; ошибки/таймауты с известным исходом — bad. Недоставленная телеметрия и неполный замер — unknown, а не быстрый успех. `eligible = good + bad + unknown`; coverage = `(good + bad) / eligible`.
- Публикуются измеряемая доля `good/(good+bad)` и консервативная нижняя оценка `good/eligible`. SLO нельзя помечать зелёным, если он выполняется только после удаления unknown. Известные зависания не переводятся в excluded из-за низкой частоты callback.
- Для сессионных долей предложен минимум 100 подходящих сессий; для действий — 500 завершённых наблюдений; для отдельного task pattern — 100 попыток. Ниже этого — «недостаточно данных», видны числитель/знаменатель и доверительный интервал. Эти пороги не являются доказательством статистической мощности; при малом DAU допускается более длинный пилот с явно указанным окном.
- Минимум проверяется для каждого SLI/разреза, а не по общему числу событий. Предложенный нижний порог coverage — 95%; ниже или при неизвестном покрытии SLO имеет статус insufficient_data. Для Undo и завершения задачи окно дозревает пять секунд после commit; оперативный отчёт предварительный, финальные UTC-дни допускают 24 h на доставку/корреляцию запоздавших событий и затем явно версионируемый пересчёт.
- Рядом с долей показывается 95% интервал Wilson. Операции одного пользователя коррелированы: интервалы по действиям ориентировочны, сравнение релизов дополнительно группируется по сессиям/пользователям. Процентили и доли объединяются из исходных счётчиков/распределений, не усредняются из дневных p95 или процентов.

## 2. Технические SLI

| ID | Показатель | Формула / измерение | SLO |
|---|---|---|---|
| TECH-01 | Drag / pan / zoom smoothness | Доля медленных активных секунд внутри сессии; затем доля сессий, удовлетворяющих условию плавности | **>94%** подходящих сессий плавные; условие внутри сессии ниже — предложение |
| TECH-02 | Action Latency | Число валидных пользовательских команд с видимым результатом `<100 ms` / число таких команд с известным исходом | Предложено **>=99%**; отдельно для каждого базового типа команды |
| TECH-03 | Initial Canvas Ready | Сессии, в которых первая подходящая загрузка достигла `canvas_ready` за `<3 000 ms` / сессии с такой загрузкой и известным исходом | Предложено **>=95%**; cold и warm отдельно |
| TECH-04 | Long main-thread blocking | Сумма `max(0, longTask.duration - 50 ms)` в активных интервалах / длительность этих интервалов | Диагностика причин задержек; порог после baseline |
| TECH-05 | Save confirmation latency | Сохранения с серверным подтверждением и видимым статусом «Сохранено» за `<1 000 ms` / завершённые сохранения | Предложено **>=99%** при нормальной сети; ошибки и зависания не считаются быстрыми |

### TECH-01. Плавность

В браузере используется `requestAnimationFrame` и монотонные timestamps; на сервер не отправляется событие на каждый кадр. rAF отражает **возможность обновления кадра**, а не доказывает физический показ нового изображения. Для выбранного renderer также проверяется, что изменение координат/масштаба действительно дошло до представления. В лаборатории сопоставить rAF-профиль, commit renderer и запись кадров; при freeze сцены живой rAF не должен давать успешный результат.

Период кадра при 60 Hz — около 16,67 ms. Частота монитора, фоновые вкладки и планирование браузера влияют на rAF; 120/144 Hz не являются обязательной целью MVP. Производительность устройства учитывается в разрезах; плохие результаты нельзя исключать, объявив устройство медленным. [Rendering performance](https://web.dev/articles/rendering-performance), [requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame).

**Предложенная измерительная конвенция v1:**

1. Активный интервал начинается при изменяющем сцену drag/pan/zoom и заканчивается после завершения соответствующего визуального обновления. Пауза без движения после уже отображённого изменения в технический интервал не входит; она остаётся в UX-02. Если обновление ожидается или callback задержан, этот промежуток не вычитается.
2. По timestamp формируются секундные окна активного времени. Короткие интервалы можно накапливать до одной секунды; между жестами не создаётся искусственный frame gap. Частота = число rAF callbacks / активная длительность; это `estimated_fps`.
3. Диагностика пользователя сохраняется буквально: `raw_slow_second_share = N(estimated_fps < 60) / N(active_seconds)`. Для границ окон дополнительно используется `budget_slow_second_share = N(callbacks < 59 за 1 s) / N(active_seconds)` — **предложенный допуск одного callback** при целевой частоте 60 FPS. Допуск является согласуемым послаблением, а не доказательством буквальных 60 FPS. Оба значения публикуются: квантизация 59/60 на границе секунд иначе давала бы ложные провалы.
4. **Плавная сессия**: не более 5% её активных секунд budget-slow, нет foreground-gap `>100 ms` при ожидающем обновлении и нет обнаруженного freeze renderer. Это новое внутрисессионное условие предложено для согласования; пользователь задал только внешние `>94%` сессий.
5. Для сессионного SLO нужно не менее пяти активных секунд, подсчитанных по прошедшему времени, а не числу пришедших callbacks. Короткие сессии видны отдельно. Остаток <1 s участвует в диагностике длинных gaps, хотя не участвует в доле полных секунд. Утраченный остаток или неполная регистрация — coverage gap.
6. Длинный callback gap раскладывается по затронутым окнам, включая окна без callbacks. Запрещено считать только окна, для которых успел сработать rAF. При переходе вкладки в hidden интервал завершается; промежуток hidden не выглядит зависанием.

Дополнительно: p50/p95/p99 frame interval, число gaps >50/>100 ms, максимальный gap, время pending visual update и отсутствие движения renderer при поступающих input. Допуск и версия алгоритма сохраняются с агрегатами; данные разных конвенций несопоставимы без пересчёта.

### TECH-02. Задержка действия

Называть показатель **Action Latency**, а не Time to Interactive. Измерение стартует с timestamp ввода, который завершает намерение: drop на порт для link creation, click добавления блока, Enter/blur сохранения поля, pointerup resize, keyboard/menu Undo. Время выбора второго порта или набора текста в техническую задержку не входит.

Конец — результат нужной команды отражён renderer и прошёл visual-ready checkpoint. Измерение от входа в JS-handler теряет input queue delay и потому не подходит как основной старт. Считаются все валидные команды, включая не завершённые из-за ошибки. Невалидный жест соединения учитывается в UX-04; latency сообщения об ошибке — отдельный диагностический тип операции.

Основной замер: User Timing marks + привязка operationId к завершённому изменению представления. Fallback `visual_ready_proxy_v1`: после DOM/renderer commit соответствующей команды дождаться двух последовательных rAF при видимой вкладке. Это консервативный **proxy**, а не API подтверждения реального paint; его погрешность проверяется профилировщиком. React state update, HTTP 200 и первый rAF до paint не считаются готовым изображением. При неподдерживаемом probe результат unknown, измерительный метод хранится в событии.

Event Timing и INP — дополнительные диагностики. Event Timing не измеряет continuous pointermove/wheel/drag и по умолчанию выдаёт только достаточно медленные события. Поэтому по числу PerformanceEventTiming entries нельзя получить знаменатель всех быстрых операций. Для async-изменения схемы next paint входного события может не содержать нужную связь. [Event Timing — рабочая спецификация W3C](https://www.w3.org/TR/event-timing/), [User Timing](https://www.w3.org/TR/user-timing/).

Отдельно хранить input delay, время reducer/commit, visual completion proxy и общий end-to-end duration. В основном SLI используется общий duration, без округления перед сравнением: 99,9 ms — good, 100 ms — bad. Событие без результата через 2 s при живом foreground collector — bad timeout; это уже нарушение 100 ms, а не повод удалить операцию.

Базовые классы для отдельного SLO: node.create, node.move.commit, link.create, text.commit, resize.commit, object.delete, undo и redo. Выделение и движение указателя не используются, чтобы дешёвые частые события не скрывали задержки создания связи. Начало move/resize commit — финальный pointerup; плавность предшествующего движения измеряет TECH-01.

### TECH-03. Готовность схемы

Собственная отметка `canvas_ready` означает: документ получен и валидирован; объекты и связи первоначального viewport размещены; необходимые для размеров шрифты готовы; обработчики действий активны; пройден visual-ready checkpoint. Skeleton, пустой контейнер редактора или ответ API без отрисовки не считаются готовностью. Пустой валидный холст считается готовым, когда видны рабочая область и доступный инструментарий.

Начало для прямого cold-open существующей схемы с действующей сессией — `navigation.startTime`. Для первого явного выбора «Загрузить» — timestamp подтверждающего ввода. Ожидание ввода пароля или выбора пользователем домена не включается. В отчёте эти пути разделены; последующие загрузки — `canvas_switch_ready`, отдельный диагностический ряд с тем же предложенным порогом 3 s.

Основной сессионный SLI использует первую подходящую попытку: быстрый retry не стирает первый провал. Ошибка загрузки — bad; отсутствие ready за 3 s уже не может стать good. Позднее завершение сохраняет duration, а после 10 s живой collector фиксирует timeout. Закрытие/крах раньше порога без достаточного результата — unknown, не успех.

FMP и TTI удалены из соответствующих оценок Lighthouse; LCP/FCP полезны для загрузки оболочки, но не определяют готовность конкретного документа в SPA. Здесь закрепляется собственный контракт, а не переименовывается стандартная browser metric. [FMP](https://developer.chrome.com/docs/lighthouse/performance/first-meaningful-paint), [TTI](https://developer.chrome.com/docs/lighthouse/performance/interactive).

### TECH-04/05. Дополнения

Long Tasks / Long Animation Frames включаются только при поддержке API. Отсутствие поддержки — unavailable, не нулевая блокировка. Перекрывающиеся интервалы нельзя суммировать дважды. TECH-04 — main-thread blocking diagnostic, а не стандартный Lighthouse TBT, у которого другое окно. [Long Tasks API](https://www.w3.org/TR/longtasks-1/).

Save confirmation включает браузер → сеть → проверку/запись БД → браузер → показ подтверждения. Backend p95 save в NFR-03 остаётся отдельным диагностическим бюджетом. 412 конфликт и 401 — известные неуспехи пользовательской операции; публикуются reason breakdown, даже если сервер обработал их быстро. Save SLO не применяется к длительному AI job.

## 3. Product/UX SLI

Метрики фиксируют действия, но сами по себе не устанавливают причину. Undo может означать изменение архитектурного решения, долгий drag — сравнение вариантов размещения, дополнительные клики — другую задачу. Для расследования сопоставлять их с технической задержкой, типом операции, сценой и контролируемым тестом. Один интегральный «балл удобства» не вычисляется.

| ID | Показатель | Формула | SLO / применение |
|---|---|---|---|
| UX-01 | Быстрая отмена / действия без быстрой отмены | `micro_undo_rate = U5 / A5`; `no_quick_undo = 1 - U5/A5` | **no_quick_undo >90%**, эквивалентно micro_undo_rate <10%; индикатор, не измерение истинной ошибки UX |
| UX-02 | Длительное удержание при drag | `long_drag_excess = sum(max(0,duration-5 s)) / total_drag_time`; дополнительно эта же сумма / activeSessionTime | Диагностика и сравнение версий; абсолютный SLO после baseline |
| UX-03 | Число кликов на стандартную задачу | Среднее, median, p95 clicks per taskAttempt; excess = max(0, clicks-baselineClicks) | Для P1 предложен бюджет 3 клика и >=90% успешных попыток в бюджете; baseline уточняется прототипом |
| UX-04 | Эргономика соединения | RUM: `valid_gesture_successes / eligible_completed_connect_gestures`; отдельно размеченный first-attempt: intents, завершённые первым жестом / известные intents | **>87%** для каждого отдельно измеренного ряда; их знаменатели не объединяются |
| UX-05 | Выполнение стандартной задачи с первой попытки | Успешные taskAttempts без invalid gesture/ошибки/быстрого Undo в пределах task budget / taskAttempts с известным исходом | Предложено **>90%**; по каждому taskPattern, отдельно от UX-01 |

### UX-01. Микро-отмены

`A5` — зафиксированные, изменяющие документ пользовательские команды, для которых полностью наблюдались следующие пять секунд либо уже зарегистрирована отмена в этом окне. `U5` — команды из A5, отменённые через `0 <= undoTime - commitTime <= 5 000 ms`.

- Корреляция по undo targetCommandId, а не близости двух произвольных событий. Undo/Redo, загрузка, автодействия и no-op не становятся новыми исходными командами A5. Сам Undo учитывается в TECH-02.
- Считать клавиатуру, меню, кнопку и жест одинаково. Несколько pointermove одного drag — одна команда; групповое удаление — одна команда, даже если удалило десять объектов.
- Отмена команды считается один раз. Последующий Redo не удаляет факт микро-отмены. Обычное удаление созданной связи — отдельное действие, не выдуманный Undo; его можно анализировать отдельно как reversal.
- Если сессия закрылась через 2 s после команды без Undo, это right-censored observation, а не «действие без отмены». Уход в hidden не останавливает прошедшие пять секунд, но снижает полноту наблюдения; правило coverage сохраняет unknown.
- Учитывать распределение по node.move / link.create / resize / text.edit. Частые отмены текста нельзя автоматически приписать размеру портов или snapping.
- Рядом проверять доступность/работоспособность Undo: сломанная кнопка не должна выглядеть улучшением UX-01. Для повторного исполнения через Redo создаётся executionId, но оно не меняет уже учтённый исход первоначальной команды и не добавляет новую исходную команду A5.

Пример: из 100 полностью наблюдаемых команд девять отменены в 5 s → 91% без микро-отмены, цель выполнена. Десять → ровно 90%, строгая цель не выполнена. Эти действия не называются доказанными ошибками пользователя.

### UX-02. Время удержания

Drag начинается после активации переноса, а не с любого pointerdown, заканчивается drop/cancel. Время после первых пяти секунд считается избыточным относительно выбранного порога, без вывода о когнитивном состоянии. Обычный drag, pan/zoom, resize и создание связи имеют разные категории.

Пример: переносы 2, 8 и 12 s → excess = 0+3+7 = 10 s; total drag = 22 s; long_drag_excess = 45,45%. Если activeSessionTime = 120 s, дополнительная сессионная доля = 8,33%. В числитель не включаются целиком все 20 секунд двух длинных переносов.

Дополнительно: доля drag длительностью >5 s, p95 duration, stationary hold после последнего движения, cancellation rate. Потеря pointer capture и уход в фон фиксируются как interrupted с причиной; известное foreground-время и excess не исчезают, незавершённый tail помечается unknown. Значение не именуется «зависанием мысли» и не используется как автоматическое доказательство плохого auto-layout, которого в MVP может не быть.

Завершённые отменённые drag входят в обе суммы времени наравне с успешными. При total_drag_time = 0 результат N/A, а не 0%; при activeSessionTime = 0 дополнительная сессионная доля тоже N/A.

### UX-03. Клики

Task pattern определяется версией сценария и конкретным конечным состоянием. Для P1 предложено: добавить компонент из палитры, заполнить непустое описание, завершить редактирование. Счёт начинается с первого обращения к соответствующему инструменту и заканчивается commit описания/явным отказом/таймаутом. Такой clickstream видит только попытки после начала инструмента; трудность найти инструмент оценивается в управляемом сценарии с явным task_start.

Нормализация: один физический tap/click считается один раз; pointerdown/up/click не являются тремя кликами. Double-click = два клика. Текстовые символы не считаются кликами; keyboard activations и pointer clicks сохраняются раздельно. Порог 3 — предложение к маршруту P1, а не уже измеренное свойство интерфейса.

Среднее по успешным задачам показывается вместе с количеством всех попыток, отказов, таймаутов и долей завершений. Уход пользователей не должен улучшать метрику за счёт исчезновения неудачных попыток. Для неуспехов публикуются clicks until failure/abandon; они не трактуются как стоимость успешного выполнения. Сравниваются одинаковые taskPatternVersion, опыт пользователя (если известен без профилирования), сцена и input mode.

Релиз с ростом среднего с 3 до 6 кликов при неизменном сценарии удваивает наблюдаемую стоимость взаимодействия; причина проверяется по шагам. Это не универсальная метрика качества всего продукта. Автоматически угадывать намерение пользователя по близким кликам не требуется.

### UX-04. Эргономика связей

Один gesture начинается после выбора исходного порта и входа в режим соединения; заканчивается первой попыткой drop/подтверждения цели. `link_connect_success` — валидная связь создана и видна без повторного жеста. `link_connect_fail` содержит reason: miss_target, incompatible_port, duplicate, validation_error, render_error, timeout, unexpected_pointer_cancel.

Суммировать success и fail нужно по уникальному gestureId; повторная отправка события/React callback не создаёт ещё одну попытку. Повтор drag после промаха — новая попытка: один fail и один success дают 50%, а не «в итоге 100%». Drop рядом с портом считается success только если фактическое snapping создало корректную связь. Исправление невалидной связи после drop не делает первую попытку успешной.

Явные Escape/Cancel до выбора цели исключаются из основной доли как отказ от действия, но всегда показываются отдельными cancellation/abandonment counters и inclusive completion rate. Технический pointercancel не считается намеренным Escape. Для keyboard connect аналог — один цикл source → target confirmation, отдельная группа.

Клик мимо исходного порта, не начавший режим соединения, в этой метрике не наблюдается. Это ограничение измерения, не нулевой промах. Task UX-05 и управляемая проверка обнаружения/попадания в source port дополняют её. Доля >87% не означает >87% всех неявных намерений пользователя.

**Настоящее выполнение с первой попытки** измеряется дополнительно в размеченном сценарии P2 или при явно зарегистрированном connectionIntentId с известными source/target: numerator — intents с успехом первого жеста; denominator — все такие intents с известным исходом, включая явно прекращённые. Один промах и последующий успех в рамках intent дают gesture success 1/2 и first-attempt success 0/1; eventual completion = 1/1. Намерения из произвольного clickstream не угадываются. Если такого покрытия нет, first-attempt ряд unavailable, а полевой gesture success не называется его эквивалентом.

### UX-05. Завершение задачи

Предложенные pilot patterns: P1 создать блок + описание (budget 30 s), P2 соединить два совместимых порта (10 s), P3 добавить внешнюю подпись и завершить resize (20 s). Все task budgets — активное foreground-время, версия сценария фиксируется. Контекстные условия и старт в реальной аналитике должны быть явно доступны; отсутствующий task_start не восстанавливается предположением.

Success — ожидаемое состояние достигнуто, не было отмеченной неудачной попытки и в последующие пять наблюдаемых секунд не произошло Undo команды результата. Known failure/timeout — bad, явно прекращённая задача — abandoned и входит в знаменатель task success, потеря наблюдения — unknown. First-pass success, eventual completion, time-to-task и abandonment показываются раздельно.

## 4. Контракт телеметрии

Collector — модуль frontend рядом с обработчиками команд/renderer. Он не меняет documentRevision, semanticContentHash, undo-историю и результат оценки. Тексты, названия блоков, координатный трек, содержимое клавиатурного ввода, схемы и AI-key не отправляются. Допустимы тип операции, размер сцены по корзинам, длительности, счётчики и случайные correlation IDs.

Общая оболочка: `telemetrySchemaVersion`, `metricDefinitionVersion`, `eventId`, `editorSessionId`, `sequenceNumber`, `occurredAtUtc`, `sessionOffsetMs`, `releaseId`, `inputMode`, `sceneSizeBucket`, `measurementMethod`, `payload`. `operationId`, `commandId`, `taskAttemptId` добавляются по типу. Сервер связывает batch с вошедшим пользователем; клиент не задаёт owner_id. Монотонная sessionOffsetMs сохраняется для порядка; UTC используется для окна отчёта с проверкой clock skew.

| Событие | Минимальные специфические данные |
|---|---|
| editor_session_started / summary | причи́на старта/окончания, foreground/active duration, started/completed/lost counters, последний sequenceNumber |
| canvas_load_started / ready / failed | loadAttemptId, kind cold/first_open/switch, timings, reason; готовность по TECH-03 |
| edit_action_started / completed / failed | operationId, commandId при commit, actionType, inputTimestamp, duration, outcome |
| command_undone | targetCommandId, undoMethod, commit-to-undo duration |
| drag_summary | gestureId, drag kind, duration, stationary/excess/foreground duration, committed/cancelled/interrupted |
| render_window_summary | session/window ID, active duration, callbacks, slow counts raw/budget, max gap, pending update duration, freeze flag, coverage |
| link_connect_started / success / fail / cancelled | gestureId, method, outcome/reason; один terminal outcome |
| task_started / completed / failed / abandoned | taskAttemptId, patternId/version, clicks, keyboard activations, duration, undo observation completeness |
| save_started / confirmed / failed | saveAttemptId, total and stage durations, outcome/reason |
| telemetry_health | generated/sent/acknowledged/dropped counters, buffer overflow, unsupported probes, observer overhead |

`completed` не задним числом превращается в `failed` при позднем Undo: связь outcome и последующего command_undone сохраняется для аналитики. Для task success применяется пятисекундное окно. Unknown не передаётся как success ради закрытия агрегата. Порядок получения HTTP-batches не является порядком событий; eventId/sequenceNumber обеспечивают dedup и восстановление порядка.

Для будущей итерации предложен `POST /api/v1/telemetry/batches`, строгая валидация event type и разрешённого payload, не более 50 событий / 64 KiB; cookie auth, Origin/CSRF, rate limit. Ответ 202 означает запись/принятие batch для агрегации, а не успешность измеренных действий. Возможные таблицы telemetry_events и telemetry_daily_aggregates — в существующем PostgreSQL; дополнительный брокер или отдельный аналитический сервис не нужны. Этот endpoint и таблицы не включены в текущий API/DDL/план MVP; полная машинная схема потребуется только при принятии итерации наблюдаемости.

Начальное sampling — 100% подходящих сессий при заданном DAU, без регистрации каждого pointermove/кадра. Доставка раз в 15 s вне активного жеста либо после его завершения; последняя отправка при pagehide — best effort и не гарантирует полноту. Локальный буфер ограничен 200 событиями, retry — не более двух с backoff; eventIds сохраняются. Переполнение увеличивает dropped counter; telemetry сбой не мешает сохранению/работе редактора. Не использовать localStorage/document save как синхронную запись на каждое событие.

Для будущей итерации предложено хранить raw события семь суток, дневные агрегаты 90 суток. Малое число категорий и индексы по session/time/release; не сохранять полный user agent или fingerprint. Доступ к аналитике — владельцу приложения; состав отчётного UI будет отдельным решением. Значения считаются на фактически полученных данных, поэтому отдельно показывается оценка недоставленных событий и не завершившихся сессий по серверным starts/последовательностям. Сессии, полностью невидимые collector, не объявляются успешными: диагностика покрытия сравнивает bootstrap/загрузки API с telemetry starts, а отказ JavaScript до этих точек требует синтетического мониторинга.

Оверхед collector проверяется A/B-прогоном одного сценария: предложено p95 времени его синхронного callback <1 ms; увеличение p95 Action Latency не более 5 ms; сетевой/CPU overhead без обработки raw pointermove на сервере. Сбор телеметрии сам не должен создавать измеряемый jank.

## 5. Отчёт, baseline и действия при нарушении

- Отдельные строки TECH-01…05 и UX-01…05, версия метрики/релиза, окно, counts, coverage, unknown/excluded с причинами, доверительный интервал и поддержка probes. Цель неизвестной метрики не подменяется зелёным нулём.
- Технический провал в синтетическом сценарии при приёмке блокирует выпуск затронутого редакторского пути до исправления. Field-провал запускает разбор по типам действий/сценам/браузерам и проверку rollback; метрики не блокируют пользователей.
- Превышение UX-01/02/03 требует проверки поведения и сценария. Автоматически убирать Undo, ограничивать свободу размещения или делать случайное snapping ради чисел запрещено.
- Для TECH-01 error budget — менее 6% плохих сессий; UX-01 — менее 10% микро-отмен; UX-04 — менее 13% неуспехов. Из-за строгого `>` точное равенство порогу означает нарушение. Цели с `>=` допускают равенство.
- Сначала собрать baseline на фиксированной сцене и небольшой группе пользователей; затем сравнивать одинаковые patterns/input modes и учитывать user learning. Для UX-02 абсолютный порог не выдумывается до наблюдений; публикуются duration distributions и изменения к baseline.
