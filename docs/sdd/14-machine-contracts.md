# sysdes — машинные контракты baseline 1.0

Дата выпуска: 2026-09-06. Решения приняты ответами 1–26. Контракты описывают будущую реализацию; проверка файлов не является проверкой приложения.

## Форматы и ответственность

| Артефакт | Что определяет |
|---|---|
| [canvas-document.schema.json](contracts/canvas-document.schema.json) | Полный semantic/layout, HLD/ER/Sequence, контекст, тексты и ссылки |
| [canvas-export.schema.json](contracts/canvas-export.schema.json) | Пользовательский JSON: версия, имя, домен, provenance и document |
| [semantic-export.schema.json](contracts/semantic-export.schema.json) | Текстовый AI-контекст с evaluationType, diagramIds и referencedObjects, без layout |
| [rubric.schema.json](contracts/rubric.schema.json) | Неизменяемая рубрика, целые веса/уровни, альтернативы, группы взаимоисключения, referenceScore=1500 |
| [evaluation-input.schema.json](contracts/evaluation-input.schema.json) | Серверный снимок семантики, baseline/delta, рубрики, модели/настроек, hash и deadline |
| [provider-result.schema.json](contracts/provider-result.schema.json) | Строгий AI JSON: решение с уровнями зачёта либо диагностика 1–5 |
| [evaluation-result-v2.schema.json](contracts/evaluation-result-v2.schema.json) | Сохранённый отчёт с проверенной привязкой, серверными суммами и процентом |
| [api-models.schema.json](contracts/api-models.schema.json) | DTO HTTP, включая различие общего запуска и выбранных диаграмм, записи каталога с уровнем раскрытия и публикацию решения |
| [openapi.json](contracts/openapi.json) | OpenAPI 3.1.1: 24 пути, 31 операция, cookie/CSRF, ошибки и встроенные схемы |

Отдельные `*.schema.json` ведутся вручную и являются источником истины. `openapi.json` из них не редактируется руками: он собирается [scripts/build_openapi.py](../scripts/build_openapi.py), который встраивает схемы в components и задаёт пути/операции. После изменения схемы или набора операций нужно перезапустить генератор и [verify_specs.py](../scripts/verify_specs.py); проверка расхождения components и отдельных схем выполняется автоматически.

Ранние черновые генераторы самих схем и примеров не сохранены как рабочий инструмент: содержимое контрактов после их запуска правилось вручную, и повторный запуск сейчас не воспроизвёл бы зафиксированные файлы. Восстанавливать их без сверки байтов нельзя.

JSON Schema — Draft 2020-12; объекты закрыты для неизвестных полей. Поля schemaVersion=1 относятся к документу/экспорту/рубрике, schemaVersion=2 — к результату. Это независимые версии форматов. Исторические [evaluation-result.schema.json](contracts/evaluation-result.schema.json) и [evaluation-result.json](examples/evaluation-result.json) не используются текущим HTTP-контрактом.

OpenAPI содержит встроенные копии схем для автономной проверки. Первичны отдельные JSON Schema; изменение требует обновить соответствующие компоненты OpenAPI и проверить примеры. Свойства response/read-only не подменяют серверную проверку владения и неизменяемости provenance. [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html).

## Структурная и семантическая валидация

Схема проверяет типы, enum, обязательные поля и диапазоны. Дополнительные проверки обязательны на backend перед сохранением и перед AI-вызовом:

- До JSON Schema: предел байтов, корректный UTF-8, отсутствие повторных JSON-ключей, NaN/Infinity, непарных суррогатов; числа должны представляться конечными binary64, идентификаторы/счётчики не превышают безопасный целочисленный диапазон JavaScript.
- Один общий namespace ID в документе, не более 2000 адресуемых объектов. Все ссылки имеют существующую цель допустимого типа. Layout ссылается на соответствующие блоки/диаграммы/annotations, не на произвольные строки контекста.
- `layout.ports` ссылается только на существующие блоки, `layout.edgePorts` — только на существующие связи; порт принадлежит одной из двух противоположных сторон блока. Ссылка на исчезнувший порт не делает документ невалидным: она читается как значение по умолчанию, потому что порты — оформление, и терять из-за них содержание нельзя.
- HLD endpoints принадлежат одной HLD-диаграмме, childIds допускаются у boundary; включение групп ациклично. Параллельные HLD-связи допустимы.
- ER PK/index/unique ссылаются только на поля своей сущности, FK mapping — на поля заявленных source/target, foreign_key требует mapping. Неизвестные типы/nullable остаются null, логическая связь допустима без FK.
- Sequence order в одной диаграмме равен 1..N без повторов. Return адресует более ранний sync с обратной парой участников; self-call допустим. representedObjectId — HLD-компонент либо null.
- Короткое имя блока (`shortName`) уникально в пределах своей диаграммы; отсутствие имени допустимо. На блоке не более трёх внешних annotations. Контекст и notes ссылаются на существующие диаграммы, requirementRefs — на требования. Numeric range с известными границами требует lower <= upper; для других comparator upperValue=null.
- Уровень раскрытия карточки — серверный контроль доступа, а не подсказка отображения: ответ карточки содержит только раскрытую часть схемы, скрытые объекты не отдаются в нём ни в каком поле. Условие задания (context) раскрытием не управляется и присутствует на любом уровне. Чтение записи целиком — отдельная операция с собственным operationId, и то, что она возвращает весь документ, является её назначением, а не утечкой карточки. Звёзды сервер вычисляет как сумму уровня раскрытия (3, 2 или 1) и резерва сложности записи (0..2) и не принимает это значение от клиента; результат лежит в 1..5. Частично раскрытая схема HLD остаётся связным поддокументом: висячих ссылок на скрытые объекты в ответе нет.
- Публикация в каталог принимается только при неустаревшем общем отчёте с maximumReached; сервер сам сверяет документ со снимком оценки, процент от клиента не принимается. Версии записей каталога неизменяемы, тэг экспорта уникален в нормализованной форме, а запись без утверждённой владельцем рубрики не является источником оцениваемого задания.
- Домены ресурса/document/template совпадают; владелец, домен и provenance неизменны при save. Шаблон клонируется с новыми ID и originTemplateObjectId для сопоставления с исходной версией. Объекты без происхождения считаются авторскими.
- Полный набор общих diagramIds определяет сервер. Для диагностики допустим непустой набор одного типа и замкнутый контекст. referencedObjects несут минимальные данные без висячих исходящих ссылок; объект включается один раз. Snapshot содержит конкретную утверждённую рубрику, а не данные клиента о её весах.

JSON Schema не выражает FK, уникальность ID внутри разных массивов, owner-политику, гонки транзакций, атомарность квот или конечный timeout. Эти инварианты покрываются отдельными unit/integration/browser-проверками в плане; [verify_specs.py](../scripts/verify_specs.py) уже проверяет рискованные инварианты на артефактах-примерах, но не является runtime-валидатором приложения.

## Канонизация и hash

Используется JSON Canonicalization Scheme, RFC 8785: детерминированные JSON-байты без пробелов между токенами, сортировка ключей и стабильное представление чисел/строк. JSON-строки пользователя не переводятся и не нормализуются по Unicode. SHA-256 записывается 64 строчными hex-символами. [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785).

До JCS сортируются массивы-множества записей по ID: diagrams, nodes, edges, entities, relationships, participants, fields, annotations, notes, requirements, acceptanceCriteria, technicalParameters, assumptions, constraints, referencedObjects, indexes, uniqueConstraints. diagramIds, requirementRefs, childIds и delta ID-наборы сортируются по ID. Messages сортируются по order. Порядок primaryKeyFieldIds, fieldIds индекса и пар fieldMapping сохраняется; значимые массивы не сортируются универсально. Массива «все значения сортируются» нет.

semanticContentHash = SHA-256(JCS(normalize({exportVersion, evaluationType, diagramIds, semanticExport, templateBaseline, semanticDelta}))). Для хеширования копий semanticExport/templateBaseline исключаются корневой rubricVersion и templateProvenance.rubricVersion: они относятся к настройкам оценки. Остальной provenance и сам pinned rubricVersion сохраняются в исходном snapshot и документе. Layout, имя, canvasId, revision, timestamps, model и prompt/rubric settings в эту проекцию не входят.

evaluationInputHash = SHA-256(JCS({semanticContentHash, promptVersion, rubricVersion, modelId, modelParameters, providerPolicy, reportLocale})). Здесь rubricVersion — непрозрачная строка rubricId:version, связанная с неизменяемым содержимым рубрики. Создание новой версии не переписывает существующие холсты. SemanticDelta вычисляется по сравнению с выбранной областью исходного шаблона через originTemplateObjectId: добавленные ID — текущие, удалённые — исходного шаблона, изменённые — текущие. Изменённым считается любое семантическое свойство, а не координаты. Для Custom templateBaseline=null и delta содержит все текущие объекты как addedIds. Пример использует сохранённые ID для наглядности сравнения, это не алгоритм клонирования.

Fixtures: [семантические байты](examples/semantic-projection.canonical.json), [байты настроек](examples/settings-projection.canonical.json), [ожидаемые hash](examples/canonical-hashes.json). Backend и frontend обязаны выдавать эти байты одинаково, включая дробные числовые параметры и Unicode. Вспомогательный Python-пакет rfc8785 используется только для проверки документов; выбор runtime-реализаций фиксируется зависимостями и cross-language fixtures.

## AI-ответ и начисление

По 24A модель возвращает только JSON по provider-result; backend выбирает соответствующую ветку solution или диагностического типа. Для structured output адаптер подставляет конкретную схему ветки и разворачивает локальные references, если это требуется поддерживаемой моделью. Несовместимость модели со схемой выявляется до включения AI; ключ/модель и денежные лимиты задаёт владелец. Обязательные данные не обрезаются и fallback на непроверенный произвольный текст не выполняется. Поддержка structured output зависит от модели/провайдера. [OpenRouter Structured Outputs](https://openrouter.ai/docs/guides/features/structured-outputs).

Для solution каждый пункт рубрики присутствует ровно один раз. AI указывает criterionId, разрешённый levelId или null, explanation и evidenceRefs. Backend сопоставляет уровень с целыми points рубрики, проверяет 0 <= points <= maxPoints, достаточность ссылки как данных (семантическую убедительность ещё оценивает AI/benchmark), исключает двойной зачёт и несовместимые положительные пункты exclusiveGroup. Обычно технологические альтернативы оформляются внутри одного пункта; нулевой уровень обязателен, полный соответствует maxPoints.

Для evaluated все уровни известны. Backend добавляет maxPoints/awardedPoints по каждому пункту, hldScore, additionalScore, rawScore, referenceScore=1500, progressPercent и maximumReached. progressPercent = min(100, rawScore * 100 / 1500), UI округляет до двух знаков ROUND_HALF_UP только итог. maximumReached = rawScore >= 1500 определяется до округления. rawScore не обрезается. Для insufficient_data общий rawScore/части/процент — null, maximumReached=false; модель не должна выдавать неизвестное за 0. Для диагностик overallScore остаётся 1–5/null, не переводится механически в 1500 баллов.

Все ссылки findings/evidence/coverage должны существовать в snapshot и иметь нужный тип; каждый must-критерий покрывается ровно один раз. Дубли, неверный уровень, выдуманная ссылка, несоответствие типа результата или неполная структура дают invalid_result. Provider не назначает evaluationId, итоговые суммы или hash. Полный отчёт получает эти поля от сервера после проверки. Числовые примеры рубрики служат только для проверки формата/арифметики, не являются утверждёнными весами стартовых заданий.

## Хранение и повторные запросы

На аккаунт до 1000 холстов, у каждого максимум один содержательный отчёт. По 23A успешный результат любой команды целиком заменяет старый результат и snapshot; недостаточность данных — содержательный результат, сетевой/форматный отказ — нет. Во время job старый отчёт доступен. Новый вход хранится временно, после ошибки лишний snapshot удаляется. Metadata jobs и финансовые обязательства не включают историю схем/текстов и не освобождают денежный резерв при замене отчёта.

Повтор Idempotency-Key не создаёт новый ресурс/job и не списывает квоту. Если исходный ресурс удалён, 410 resource_deleted не возвращает его содержимое и не создаёт заново. GET вытесненного результата с ещё сохранёнными metadata возвращает resultAvailable=false и result=null. Уничтоженные metadata дают 404. Health endpoints доступны только эксплуатационному контуру, proxy не публикует их автоматически.

## Конфигурация и готовность к запуску

Принятые по 26A ограничения — стартовые hard caps и цели приёмки, не заявленная производительность. Уменьшение серверного cap допустимо конфигурацией при корректной индикации в UI; увеличение сверх machine schema требует согласованного обновления контракта/клиента. Денежные лимиты, model ID, provider-настройки, тариф для резерва, секрет OpenRouter, TLS и адрес backup задаются оператором перед эксплуатацией. Их отсутствие не блокирует разработку/локальный mocked AI, но запрещает платный запуск.

Перед релизом измеряются SLI по 09, ресурсы/restore по 06, качество AI по согласованному контрольному набору. Это задачи реализации и приёмки, а не незакрытые продуктовые вопросы. Восемь стартовых двуязычных шаблонов с рубриками готовятся и утверждаются владельцем перед публикацией; DDL/seed-контент каталога не входит в текущую работу над спецификациями.

## Воспроизводимая проверка

```powershell
python -m venv .venv-specs
.\.venv-specs\Scripts\python.exe -m pip install -r scripts/requirements-specs.txt
.\.venv-specs\Scripts\python.exe scripts/verify_specs.py
node scripts/verify_canonical.mjs
git diff --check
```

Проверка выполняется без API-key и платных AI-вызовов. Она валидирует schemas/OpenAPI, positive/negative fixtures, ссылки, арифметику, canonical bytes и покрытие FR приёмочными сценариями. Запуск команды не измеряет FPS и не подтверждает реальную точность AI. Каталоги .venv-specs и .spec-work исключены из Git.
