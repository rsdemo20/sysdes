# sysdes — приёмка и NFR

Статус: Baseline 1.0. Все AC ниже описывают будущие проверки; приложение ещё не разработано.

Два разных уровня приёмки:

1. **Приёмка самого sysdes** — сценарии в этом документе.
2. **Критерии приёмки проектируемого приложения** — данные пользователя/шаблона на холсте. Они описываются в 03 и используются AI. Проверка схемы не доказывает достижение реальных бизнес-метрик работающей системой.

Технические проверки MVP с минимальными затратами — в [09-technical-sli.md](09-technical-sli.md): профилировщик браузера и небольшие локальные замеры. Product/UX SLI, полевые SLO по сессиям и кликстрим сохранены в [10-observability-next.md](10-observability-next.md) как развитие; их реализация и статистическое подтверждение не блокируют первый выпуск.

## Принятые цели NFR — ответ 26A

| ID | Сценарий / среда | Цель |
|---|---|---|
| NFR-01 | 1–100 DAU; предварительный пик 10 одновременно редактирующих пользователей | Сохранение не зависит от доступности OpenRouter; реальный пик подтвердить |
| NFR-02 | Принятый AI job в работающем приложении, включая очередь | Конечный статус за ≤120 секунд; успешные валидные ответы в этом окне ≥95% на согласованном benchmark |
| NFR-03 | Документ 1 MiB, 10 активных пользователей, app/DB на одном хосте, без учёта WAN | p95 save/load ≤500 ms; ошибки измеряются отдельно от latency |
| NFR-04 | Desktop Chromium/Firefox, viewport 1440×900; 150 блоков, 250 связей, 100 подписей, 40 сообщений Sequence; монитор 60 Hz в лаборатории | Цель 60 FPS и Action Latency <100 ms, включая input → видимый символ отдельно от text.commit. Быстрый ввод и ввод во время auto PUT проверяются на той же сцене; метод по 09/12. Полевое >94% сессий и >=99% действий — будущие цели, не статистическое условие выпуска MVP |
| NFR-05 | Один app, postgres и TLS proxy; хост 2 vCPU / 2 GiB RAM; обычная нагрузка из NFR-01 | Рабочая цель суммарного RSS сервисов ≤1 GiB; подтвердить нагрузочным тестом, не выдавать за измерение |
| NFR-06 | Build Docker runtime image | Предлагаемый compressed app image ≤250 MiB; runtime без Node/toolchain; отдельно измерять image size и RSS |
| NFR-07 | Два пользователя, разные холсты и job | Ни один тест доступа по чужому ID не раскрывает/не изменяет данные |
| NFR-08 | Backup/restore на чистое окружение | Предложено RPO ≤24 h, RTO ≤2 h; проверяется практическим восстановлением |
| NFR-09 | Валидные канонические fixtures HLD/ER/Sequence | Ни один значимый объект, подпись, критерий приёмки или порядок сообщений не теряется |
| NFR-10 (Deferred) | Product/UX SLI по действиям, drag, clickstream и подключению | Определения и целевые >90% / >87% сохранены в 10; сбор, расчёт и приёмка этой аналитики отложены |
| NFR-11 | Первая загрузка схемы, cold-open и первый явный выбор отдельно | canvas_ready <3 s в контрольных прогонах; сеть и разбор включены, ожидание ввода пользователя исключено; полевая доля >=95% отложена |
| NFR-12 | Пользователь нажимает «Сохранить» / Ctrl+S / Cmd+S, нормальная сеть | Предложено видимое подтверждение ручного сохранения <1 s, включая ожидание координатора. Минутный интервал автосохранения не входит в эту latency; будущая полевая доля >=99% не требует collector в MVP |
| NFR-13 | Затраты на измерения | Профилировщик и малые dev/test замеры в существующих сценариях; без отдельного runtime collector, API, хранилища событий и dashboard в MVP |

DAU не равен числу параллельных запросов. До фиксации ресурсных лимитов требуется короткое измерение на типовой машине и target-host; снижение RSS не должно ухудшать редактирование или приводить к потере сохранений.

## Качество AI

Предлагаемые пороги для pilot benchmark (24 решения, описаны в 04):

- 100% случаев имеют структурно корректный сохранённый результат либо явно отмеченную ошибку; невалидный ответ никогда не маскируется.
- У ≥95% запусков выбранной модели — валидный содержательный ответ в 120 секунд; отдельно измерять успешность, latency, расходы и причины отказов.
- Точность существенных замечаний ≥80%; полнота заранее размеченных критических/существенных проблем ≥80%. Разметка архитектором; ошибки и ложные замечания перечисляются.
- Не менее 90% итоговых баллов отличаются от согласованной экспертной оценки не более чем на 1; набор слишком мал для заявления о статистической гарантии.
- Каждый reference валиден относительно snapshot; каждое заявление о невыполнимом бизнес-критерии содержит основание или пометку допущения.
- Для неполных решений есть вопросы и честные null-оценки; нет требования выдавать число любой ценой.

Пороговые значения приняты как цели по 26A, а не измеренные результаты. При низкой точности менять экспорт/рубрику/модель и повторять тот же benchmark; не добавлять многошаговые AI-агенты до выявления конкретной причины.

## Набор проверок реализации

- Unit/property tests: семантические инварианты, канонизация, изменение order, score/reference validation.
- Integration tests с PostgreSQL: uniqueness, ownership, conditional update, idempotency, claim/restart/deadline, атомарные лимиты.
- Browser tests: набор наиболее рискованных редакторских действий AC-04/05/06/10/18, сохранение AC-26…32, ввод AC-33…36 и доступность основных controls с клавиатуры. Таймер и пересечения запросов проверяются управляемыми часами/ответами; для доступности редактирования, текстового Undo, IME и плавности нужен реальный браузерный сценарий.
- Технические проверки AC-23…25 входят в обычную приёмку редактора: короткие воспроизводимые traces/локальные замеры. Новые clickstream tests, collector on/off, дедупликация событий и полевые отчёты не входят в план MVP. По mock timestamp нельзя утверждать реальную плавность.
- Contract tests: JSON Schema, OpenAPI, server/client fixtures; generated types не заменяют runtime-validation.
- Fault tests с mock provider: timeout, обрыв соединения, malformed output, delayed success, crash window.
- Отдельный ручной pilot с реальным OpenRouter по разрешению владельца расходов; обычный CI не выполняет платные вызовы.

После прохождения целевых проверок повторять их только при изменении связанного контракта/кода/модели либо появлении нового риска.
