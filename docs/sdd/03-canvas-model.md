# sysdes — модель холста и текстовое представление

Статус: Baseline 1.0. [JSON Schema CanvasDocument](contracts/canvas-document.schema.json), [семантический экспорт](contracts/semantic-export.schema.json) и [пример холста](examples/canvas-document.json) задают формат. Машинные и дополнительные семантические инварианты описаны в [14-machine-contracts.md](14-machine-contracts.md).

## Документ

```text
CanvasDocument
  schemaVersion
  semantic
    domainId
    templateProvenance
    rubricVersion: pinned rubricId:version
    context: requirements, acceptanceCriteria, technicalParameters, assumptions, constraints
    diagrams: HLD | ER | Sequence
    annotations
    notes
  layout
    objectPositions: objectId → x, y, width, height
    annotationOffsets: annotationId → dx, dy, width, height
    diagramFrames
    viewport
    ports: blockId → [{ id, side, offset }]
    edgePorts: connectionId → { source, target }
    edgeLabels: connectionId → { placement, dx, dy, width, height }
    textStyles: objectId → { scale, emphasis, font }
    contextPanels: scope | requirements | criteria → x, y, width, height
```

ID холста, владелец, имя, revision и даты — метаданные ресурса, не часть текста архитектуры. Смысл и layout сохраняются вместе в `solution.document`; записи React Flow генерируются из него. Запрещено использовать сериализованный внутренний state библиотеки как единственный формат хранения.

Рамка диаграммы — объект layout (`diagramFrames`), а не содержание. Новая диаграмма открывается размером примерно в три четверти видимой области и строго вне уже нарисованных рамок: ниже, пока нарисованное шире, чем выше, и правее, когда оно стало выше, чем шире. Две наложенные рамки читаются как одна путаная область, поэтому попасть наружу важнее, чем попасть рядом. Рамка меняет размер за четыре угла и четыре стороны и перемещается за свой заголовок, унося содержимое диаграммы; её тело остаётся фоном, по которому панорамируется холст. Как и вся геометрия, рамка не влияет на semanticContentHash.

Ручное и автоматическое сохранение отправляют один и тот же формат снимка `name + document`. Локальные `isDirty`, generations, таймер и статусы запросов не входят в документ и не передаются AI. Переименование и изменение layout требуют сохранения, даже если semanticContentHash не изменился. Правила подтверждения снимка без потери новых правок — в [11-canvas-saving.md](11-canvas-saving.md).

`schemaVersion` — целое число версии документа. Неподдерживаемая версия не загружается для редактирования с потерей полей. Миграции выполняются явными преобразованиями; исходник сохраняется до успешной миграции.

## Общие инварианты

1. Каждый объект, к которому можно адресовать замечание, имеет ID: диаграмма, блок, связь, ER-поле, сообщение, подпись, заметка, требование, метрика. ID уникален внутри документа и не меняется при перемещении/переименовании.
2. Диаграмма имеет `id`, `type: hld | er | sequence`, `title`; тип объекта задаётся структурой его диаграммы. Каждый объект диаграммы принадлежит ровно одному `diagramId`.
3. Между схемами создаются явные смысловые ссылки, например участник Sequence представляет HLD-компонент. Соседство и одинаковое название не устанавливают эту связь автоматически.
4. Один HLD-блок не является одновременно ER-сущностью. Для разных представлений используются отдельные ID и явная ссылка, когда она нужна.
5. Все ссылки должны разрешаться внутри документа и иметь допустимый тип. Удаление объекта удаляет зависимые связи одной undo-операцией; межсхемные ссылки очищаются с предупреждением. Сохранение висячих ссылок запрещено.
6. Неполнота допустима: пустое название, неизвестная технология или неуточнённая кратность. Структурная невалидность недопустима: повтор ID, ссылка на отсутствующий объект, некорректный тип данных.
7. `null` означает «не задано / неизвестно»; не превращается в 0, false или оценку 1.
8. Каждая копия шаблона получает новые ID. `originTemplateObjectId` связывает объект с неизменяемой версией шаблона; у добавленного пользователем объекта — null.
9. Максимум документа принят по 26A: 2 MiB UTF-8 JSON и 2 000 адресуемых объектов, включая ER-поля/подписи. Отдельное текстовое поле — до 4 000 символов; общие заметки — до 10 000. Более строгий лимит AI-входа независим от возможности сохранить холст.

## Контекст задачи

Q-02 закрыт: используются структурированные карточки критериев и свободный текст ответа. Ответ пользователя хранится в label/annotations блока, notes с diagramIds для выбранной схемы и общих notes с пустым diagramIds для всего холста. Эти тексты являются содержанием решения, а не только комментариями для чтения; они включаются в релевантный AI-вход и его semanticContentHash. Требования описывают ожидаемое поведение, текст ответа объясняет, как пользователь его обеспечивает. Ручная связь текста с criterion ID может быть необязательной: AI указывает evidenceRefs на существующие текстовые объекты, не требует переписывать ответ в форму чек-листа.


| Сущность | Поля | Смысл |
|---|---|---|
| requirement | id, kind (`functional/nonfunctional`), text, priority (`must/should/could`), diagramIds, originTemplateObjectId | Пустой diagramIds означает общее требование холста |
| acceptanceCriterion | id, text, requirementRefs, priority (`must/should`), condition, verificationMethod, diagramIds, originTemplateObjectId | Минимальное бизнес-условие приёмки; condition бывает scenario, boolean или numeric |
| technicalParameter | id, name, value, unit, basis, status (`assumption/measured`), diagramIds | Дополнительные параметры нагрузки/среды; не подменяют бизнес-приёмку |
| assumption | id, text, diagramIds | То, что пользователь принимает как допущение |
| constraint | id, text, diagramIds | Ограничения технологий, бюджета, эксплуатации, команды |

Контекст задачи показывается и редактируется на холсте, в трёх неудаляемых панелях слева от диаграмм, сверху вниз: «Задание и границы системы» (допущения и ограничения), «Требования» и «Ключевые метрики и критерии приёмки» (технические параметры и критерии). Пункты остаются структурированными — у критерия его сценарий и ссылки на требования, у метрики значение и единица, — потому что именно их читает оценка; каждый пункт правится на месте, пункты добавляются и удаляются, удалённое требование убирается из ссылок критериев. Критериев не больше восьми, как принимает оценка. Положение и размер панелей — layout (`layout.contextPanels`); пока автор их не двигал, они стоят столбцом левее самой левой диаграммы, каждая высотой по своим пунктам, а холст при открытии вписывает содержимое в экран с тем же масштабом, что и прежде, но выравнивает его по левому верхнему краю, а не по центру. Поэтому на холсте без диаграмм — Custom или начатом с одним описанием задания — панели стоят у левого края экрана, а не посередине, и место для схемы остаётся справа от них. Простые технические проверки самого редактора описаны в [09-technical-sli.md](09-technical-sli.md), будущая аналитика — в [10-observability-next.md](10-observability-next.md). Сбор событий в MVP не требуется; при его появлении телеметрия не входит в CanvasDocument, не меняет его hash/revision и не передаётся на AI-оценку.

`condition` — размеченный тип:

- `scenario`: given, when, then — проверяемое поведение без искусственного числового порога.
- `boolean`: statement, expected — бизнес-инвариант с результатом true/false.
- `numeric`: metricName, comparator (`eq/le/ge/range`), value, upperValue, unit, measurementWindow, population — бизнес-метрика, порог и условия измерения.

Для range нужны две границы с value <= upperValue; иначе upperValue = null. Числа конечные, неизвестный порог — null с явной пометкой неполноты. Для numeric обязательна единица, включая `%`/`ratio`. Изменение порога — изменение условий задачи, отражаемое относительно версии шаблона.

Примеры минимальной приёмки: повтор оплаты не создаёт второй заказ; документ переходит в архив только после обязательных согласований; сообщение доступно адресату после восстановления соединения; завершённая сделка содержит ответственного и историю изменения статусов. Числовой пример: не менее 99% подтверждённых оплат отражаются в статусе заказа в течение согласованного времени при заданных условиях.

Часть бизнес-метрик (например, конверсия продаж) зависит от факторов вне архитектуры. AI должен указывать предел применимости: схема может обосновывать поддерживающие механизмы, но не доказать достижение конверсии.

technicalParameters — дополнительный необязательный раздел для DAU, RPS, latency, объёма данных и т. п. Сервер не подставляет нагрузку из бизнес-цели без явно заданной модели. Обязательным для создания остаётся домен; неполный контекст не мешает рисовать.

## HLD

- `nodes[]`: id, shortName, kind, label, properties, originTemplateObjectId.
- Базовые kind: `actor`, `service`, `datastore`, `queue`, `external_system`, `boundary`.
- Форма не кодирует vendor. Кэш может быть datastore с `storageRole=cache`, API gateway — service с `role=gateway`.
- Вид блока рисуется общепринятой для HLD фигурой, чтобы схема читалась без легенды: `service` — прямоугольник со скруглением, `datastore` и `queue` — цилиндр (у очереди он лежит на боку), `actor` — фигура человека, `external_system` — прямоугольник с двойной левой гранью, `boundary` — рамка с пунктирной границей. У цилиндра видны оба кольца — верхнее и нижнее, иначе фигура читается как прямоугольник со скруглением. Блок с `scaled` дорисовывается двумя контурами-тенями снизу и справа: N экземпляров показываются стопкой, а не числом, которого автор не заявлял. Фигура — это способ показать kind, а не отдельное поле: она следует из kind и не хранится в документе.
- `properties` содержит ограниченный документированный набор: responsibility, technology, replicas, region, storageRole, consistency, scaled; неизвестные значения допустимы.
- `scaled` — компонент работает в нескольких экземплярах, число не заявлено. Это утверждение о решении, а не оформление: оно входит в семантический экспорт и доступно оценке. Когда число известно, оно указывается в `replicas`.
- `shortName` — короткая ссылка вида `qu3`, `gw1`, `lb2`: префикс говорит, что это за часть, число — какая именно. Поле необязательное; документ без него остаётся валидным, а редактор выводит имя из вида блока и его позиции на диаграмме. Два блока одной диаграммы не могут отвечать на одно короткое имя. Номер не переиспользуется после удаления блока: имя, молча переехавшее к другому объекту, хуже отсутствия имени, потому что на него ссылаются подписи и замечания.
- `edges[]`: id, sourceId, targetId, label, interaction (`sync/async/dataflow/unspecified`), bidirectional, protocol, originTemplateObjectId.
- Связь рисуется одним из пяти способов, и способ хранится как то, что он значит, а не отдельным полем оформления: сплошная стрелка — `sync`; сплошная в обе стороны — `sync` с `bidirectional=true`; линия без стрелок — `unspecified`; пунктирная стрелка — `async`; пунктирная линия — `dataflow`. Сплошная означает вызов, пунктир — что стороны не ждут друг друга, отсутствие стрелки — что направление не заявлено. `bidirectional` необязателен и по умолчанию считается false.
- Boundary может включать childIds и быть визуальной группой. Циклическое включение групп запрещено; сетевые циклы HLD допустимы.
- Параллельные связи между одной парой компонентов допустимы и имеют разные ID.
- Точки, к которым цепляются связи, — порты — являются layout, а не смыслом: сколько у блока портов и где они стоят, ничего не говорит об устройстве системы, это говорят связи. Поэтому добавление порта не меняет `semanticContentHash` и не видно оценке.
- У порта нет направления. Нет входа и выхода — есть свободный порт, от которого можно начать связь и к которому можно её подвести. Какой конец линии какой, определяет линия, а не точка касания.
- Порты живут на двух противоположных сторонах блока: слева-справа либо сверху-снизу. Смена ориентации переносит все порты блока на другую пару сторон; четыре стороны одновременно не поддерживаются намеренно — они читаются как шум, а не как свобода. Отдельный порт можно передвинуть по периметру, включая на другую грань.
- Кнопка «+», добавляющая порт, стоит снаружи середины своей стороны, пока середина свободна от линий. Линии рисуются поверх блоков и выходят из порта прямо, а за линию хватаются в полосе по 10 px с каждой стороны от неё. Поэтому, когда на стороне есть порт у середины — единственный, средний из трёх, пяти, семи, — кнопка отступает от середины вдоль стороны шагами по 12 px до ближайшего места, свободного от всех линий этой стороны; если такого места нет, встаёт посередине промежутка между двумя линиями, ближайшего к середине. Иначе линия ложится поперёк кнопки и забирает нажатие.
- По умолчанию HLD-блок имеет три порта: один слева и два справа. ER-сущность и участник Sequence — по одному с каждой стороны. Документ без `layout.ports` считается имеющим эти значения по умолчанию.
- `layout.edgePorts` запоминает, из какого порта проведена каждая связь. Без записи связь выходит из последнего порта и приходит в первый. Ссылка на несуществующий порт игнорируется в пользу значения по умолчанию, а не делает документ невалидным.
- Подпись связи — многострочный текст: Enter переносит строку, Ctrl+Enter или уход из поля фиксирует значение. Где и какого размера подпись нарисована — тоже layout (`layout.edgeLabels`), и на `semanticContentHash` это не влияет.
- Расположение подписи выбирается из пяти вариантов: в линии (по умолчанию, как раньше), над или под горизонтальным участком, слева или справа от вертикального участка. Участок ищется на самой нарисованной ступенчатой линии: для «над/под» — горизонтальный не короче половины ширины подписи, для «слева/справа» — заметный вертикальный; из подходящих берётся ближайший к середине линии. Если подходящего нет, берётся самый длинный участок нужного направления, а без таковых — условный центр линии.
- Подпись можно перетащить за область захвата, которая появляется у выделенной связи. Перетащенное положение хранится смещением `dx, dy` от середины линии, а не от листа: при перемещении блоков подпись идёт за своей линией. Смещение важнее выбранного варианта; выбор другого варианта сбрасывает его.
- Размер подписи меняется за контур, который появляется у выделенной связи; `width, height` равные `null` означают размер по тексту. Размер ограничен 60×20 … 480×320, чтобы подпись всегда можно было найти и чтобы одна подпись не закрывала диаграмму.
- Запись `edgeLabels` для удалённой связи удаляется вместе с ней: сервер отклоняет layout, ссылающийся на несуществующий объект.
- Карточки заметок («Свободный текст») и внешних подписей прозрачны: они лежат среди блоков и линий и не должны их закрывать. Где карточка, показывает пунктирный контур; читаемость текста держит белый ореол вокруг букв.
- Фон подписи связи прозрачный: подпись не закрывает соседние линии и блоки. Читаемость там, где текст пересекает свою линию, держит белый ореол вокруг букв. Полосы прокрутки у подписи с заданным размером видны только во время редактирования; при выходе из поля прокрутка сбрасывается к началу.
- Однонаправленная связь (стрелка или пунктир со стрелкой) при повторном нажатии той же кнопки разворачивается: `sourceId` и `targetId` меняются местами. В отличие от раскладки это смысловое изменение — стрелка говорит, кто кого вызывает. Порты, между которыми линия нарисована, фиксируются в `edgePorts` крест-накрест, поэтому линия остаётся на месте и меняется только направление.
- Текст блока, заметки, внешней подписи и подписи связи оформляется индивидуально (`layout.textStyles`): размер шагами ×0.7…×2 (`scale`), начертание обычное / жирное / курсив (`emphasis`) и одна из четырёх гарнитур — без засечек, с засечками, моноширинная, рукописная (`font`). Управление — четыре кнопки в панели самого объекта: A−, A+, начертание по кругу, шрифт по кругу. У подписи связи ER и у сообщения Sequence своей панели нет, поэтому эти четыре кнопки появляются под подписью, пока связь или сообщение выделены. Это layout: на `semanticContentHash` и оценку не влияет; запись для удалённого объекта удаляется вместе с ним.
- У HLD-блока две текстовые строки, и обе редактируются там же, где редактируется блок: название и описание. Описание пишется в свойства блока — в `technology`, если блок его называет (эту строку блок и раньше показывал первой), иначе в `responsibility`; очищенное описание хранится как `null`. Это смысл, а не раскладка: описание читает рецензент и модель. Блок делится по высоте на пятые доли: верхняя — заголовок с типом и коротким именем, средние три — название, нижняя вместе с зазорами — описание. У хранилища сверху остаётся место под обод цилиндра.
- Текст внутри блока — название и описание — выровнен по центру: блок читается как фигура с подписью. Поля сущности ER остаются выровненными влево, потому что это таблица. Проверка орфографии включена только у поля, которое сейчас редактируется: у поля, из которого вышли, красных подчёркиваний нет, и холст, который просто читают, ими не покрыт.

## ER / логическая модель данных

Глубина подтверждена ответом 11A: обязательны возможности описания сущностей, полей, PK/FK, связей и кратности; заполнение типов и индексов необязательно. Это не требование заполнить все поля перед сохранением или оценкой. Пустые необязательные значения сохраняются как неизвестные; генерация SQL вне MVP.

- `entities[]`: id, label, fields[], uniqueConstraints[], indexes[], storageNotes, originTemplateObjectId.
- Поле: id, name, dataType (свободный тип или null), nullable (`true/false/null`).
- `primaryKeyFieldIds[]` сущности сохраняет порядок составного ключа. Unique/index задаются массивами fieldIds и не выводятся только из расположения строк.
- `relationships[]`: id, sourceEntityId, targetEntityId, label, sourceCardinality, targetCardinality, fieldMapping[], enforcement (`logical/foreign_key/unspecified`).
- Кратность конца: `0..1`, `1`, `0..*`, `1..*`, `unknown`. Она означает число экземпляров сущности на этом конце на один экземпляр противоположной сущности.
- `fieldMapping[]`: пары sourceFieldId/targetFieldId. Для foreign_key source — ссылающаяся сущность, target — целевая; типы ссылок валидируются. Логическая связь может не иметь FK-полей.
- M:N допустима в логической модели; AI может рекомендовать таблицу связи, но приложение не вставляет её автоматически.
- Нормализация, индексы, партиционирование и способ хранения могут быть описаны текстом. Отсутствие этих деталей становится вопросом/замечанием, а не выдуманным значением.

В ER-блоке внутреннее текстовое поле — название сущности; строки полей являются структурированной частью блока. Это уточнение позволяет оценить ключи и типы, сохраняя минимальный инструментарий.

## Sequence Diagram

- Диаграмма описывает один сценарий и содержит `participants[]` и `messages[]`.
- Участник: id, label, role (`actor/system/unspecified`), representedObjectId (HLD-компонент или null), originTemplateObjectId.
- Линия жизни — производное отображение участника; отдельного объекта данных не требует. Замечание к линии жизни адресуется участнику.
- Сообщение: id, sourceId, targetId, order, kind (`sync/async/return`), label, replyToMessageId (или null), originTemplateObjectId.
- `order` — уникальные положительные целые числа в одной диаграмме. При вставке/перестановке порядок атомарно нормализуется в 1..N.
- Для `return` поле replyToMessageId обязательно, ссылается на более раннее sync-сообщение с обратными source/target. Для других kind — null. Асинхронный ответ оформляется отдельным async-сообщением.
- Self-call допустим. Activation bars, create/destroy, alt/opt/loop/par и вложенные фрагменты вне MVP.
- Координата Y отображает order. Команда перестановки сообщения меняет order; свободное перемещение диаграммы не меняет его. Изменение X участника меняет его положение, но не адресатов сообщений.
- Растяжение/перемещение Sequence-группы и выравнивание подписей должны проверяться в прототипе React Flow. Библиотека не считается готовым UML Sequence editor.

## Выделение и перемещение группой

Выделение — состояние редактора, а не документа: оно не сохраняется, не устанавливает isDirty и не видно оценке (D-52).

- Щелчок по блоку выделяет его одного и показывает его панель: порты, заметка, стиль текста, удаление. Панель есть только у одного выделенного объекта; у группы её нет.
- Shift и щелчок по блоку — в любом его месте, включая название, — добавляют блок к выделению или убирают его оттуда. Щелчок не ставит курсор в поле блока: это выбор блока, а не места в тексте, и открытое поле при этом закрывается с фиксацией. Рука, сдвинувшая мышь при щелчке на несколько пикселей, всё ещё щёлкает, а не тянет.
- Shift и протяжка по пустому холсту — в том числе внутри рамки диаграммы, тело которой пропускает нажатия к холсту, — рисуют рамку выделения; всё, что в неё попало, добавляется к уже выделенному. Протяжка без Shift по-прежнему двигает холст. Ctrl в выделении не участвует: у него своя работа — перенос порта по периметру и масштаб колёсиком.
- Группа перемещается целиком: за любой её блок, а после выделения рамкой — за любое место выделенной области, которая показывается лёгкой заливкой. Щелчок по области без протяжки достаётся блоку под ней. Блоки сохраняют взаимное расположение; подписи идут за своими блоками, связи — за концами. Shift и протяжка блока вне группы добавляют его к группе и несут вместе с ней; протяжка блока вне группы без Shift несёт его одного и снимает выделение группы.
- Delete удаляет все выделенные блоки одной операцией: одна отмена возвращает их все вместе со связями. Delete внутри текстового поля редактирует текст (12).
- В группу входят блоки, заметки и внешние подписи. Рамка диаграммы и панели контекста задачи в группу не входят: рамка сама несёт свои блоки, а панели — условие задачи, а не схема.

## Привязанный текст и метаданные

Текст во время ввода хранится в локальном draft, а не записывается в CanvasDocument на каждую клавишу. `text.commit` переносит его по objectId/fieldPath при blur / Enter; перед сохранением/оценкой выполняется flush активных полей. Draft не входит в формат хранения, но учитывается в dirty-state; неподтверждённый ввод не теряется при смене компонента/холста. Нормативные правила — в [12-input-isolation.md](12-input-isolation.md).

- У HLD-блока, ER-сущности и участника Sequence есть ровно один внутренний `label` (может быть пустым). Поле многострочное: переносы, введённые автором, сохраняются как часть текста, длинный текст переносится по словам и заполняет доступную высоту блока. Правила ввода и фиксации — в [12-input-isolation.md](12-input-isolation.md).
- Внешние поля — annotations с собственными id, ownerObjectId и text; максимум три на блок, допускается ноль после удаления. Команда «комментарий» на блоке без подписи создаёт её, на блоке с подписью — открывает существующую: автор, нажимающий её второй раз, хочет править написанное, а не копить вторую заметку.
- Новая подпись встаёт рядом со своим блоком с зазором в 10 пикселей и обязательно на свободное место, перебирая стороны в порядке право — низ — лево — верх. Подпись, легшая поверх блока, закрывает ровно то, что описывает.
- Подпись названа коротким именем своего блока и соединена с ним тонкой пунктирной выноской индивидуального цвета. Выноска не является связью схемы: она не несёт ни протокола, ни направления и не входит в семантику. Граница подписи слабее границы блока — заметка не должна выглядеть громче того, о чём она.
- Положение внешнего поля хранится относительно владельца, поэтому оно перемещается с ним; resize меняет только layout. Изменение размера блока сдвигает соседние блоки и выводит подпись из-под выросшего блока. Удаление поля — содержательная операция.
- Подпись связи правится на самой связи и живёт на её линии: она встаёт посередине хода, а когда там занято — сдвигается вдоль линии и немного в сторону, пока не найдёт свободное место, и переезжает вслед за блоками. Подпись всегда читается как принадлежащая своей связи, поэтому уход в сторону ограничен.
- Холст, созданный из записи каталога, получает её условие в `semantic.context`: требования, критерии приёмки и известные величины копируются с новыми ID и с `originTemplateObjectId`, указывающим на объекты записи, а ссылки критериев на требования переписываются на новые ID. Условие принадлежит документу, поэтому его видит и автор в редакторе, и модель при оценке; править его автор может как любой свой текст — это его холст.
- Свободные notes размещаются на холсте: x/y/width/height находятся в layout.objectPositions по note ID. objectPositions допускает ID базовых блоков и notes; внешние подписи используют annotationOffsets.
- Свободные notes имеют text и diagramIds; пустой список означает общий контекст. Принадлежность задаётся пользователем, а не вычисляется по геометрии.
- Скрытые атрибуты включают ID, принадлежность, происхождение из шаблона. `evaluationScore: 1..5 | null` предоставляется в представлении объекта как проекция выбранного результата оценки.
- AI-оценка и findingIds хранятся в Evaluation, не перезаписывают авторский объект. При необходимости ручной рейтинг проектируется отдельно и не подаётся модели как доказательство качества.
- Метаданные доступны через панель свойств; «скрытые» означает «не постоянно нарисованы на холсте».

## Каноническое представление для AI

Рекомендуется JSON как текст с типизированной структурой. Mermaid/PlantUML можно добавить как экспорт для человека; они не являются источником истины: свойства объектов, критерии приёмки и связи между схемами должны сохраняться без потерь.

Алгоритм подготовки входа:

1. Проверить документ и права; взять сохранённый revision.
2. Для evaluationType=solution выбрать все диаграммы и контекст холста; для hld/er/sequence выбрать diagramIds одного соответствующего типа. Включить общие и адресованные выбранным схемам требования, критерии приёмки, technicalParameters, assumptions, constraints и notes. Затем включить транзитивно все записи контекста, на которые они ссылаются: например requirementRefs включённого критерия, даже если требование адресовано другой схеме. Обход с visited IDs завершается без повторов.
3. Включить подписи и все семантические свойства выбранных объектов. Для явных межсхемных ссылок включить минимальные записи referencedObjects: id, тип, название, ответственность/схема полей по смыслу ссылки. Сводные referencedObjects не несут исходящие ссылки, которые не включены; каждый оставшийся reference входа должен разрешаться. Не подмешивать все остальные диаграммы автоматически.
4. Добавить домен, provenance, сведения о версии шаблона и вычисленные изменения этой части относительно шаблона.
5. Исключить x/y, viewport, цвета, выделение, размеры, технические данные React Flow и предыдущие AI-оценки. Технические параметры самой проектируемой системы при этом сохраняются.
6. Упорядочить ключи объектов; множества записей сортировать по стабильному ID. Сообщения сортировать по order; составные ключи и другие значимые массивы сохранять в исходном порядке.
7. Зафиксировать правила UTF-8, экранирования JSON, чисел и null в `exportVersion=1`; пробелы/переносы внутри пользовательского текста сохранять. Не применять Unicode-нормализацию и округления молча.
8. Рассчитать SHA-256 по UTF-8 байтам JSON Canonicalization Scheme RFC 8785 после сортировки семантических множеств. Точные проекции и исключение настроек рубрики — в 14; сохранены побайтовые fixtures и ожидаемые hash. JSON с повторными ключами, NaN/Infinity или непарными суррогатами отклоняется.

`semanticContentHash` вычисляется по `{exportVersion, evaluationType, diagramIds, semanticExport, templateBaseline, semanticDelta}`. semanticExport содержит выбранные схемы, замкнутый по ссылкам контекст, домен и provenance. Hash исключает canvasId, имя, documentRevision, layout, evaluationId, timestamps, deadline, model, prompt/rubric versions и сами hash-поля.

`evaluationInputHash` вычисляется по `{semanticContentHash, promptVersion, rubricVersion, modelId, modelParameters, providerPolicy, reportLocale}`. reportLocale принимает ru/en; язык UI сам по себе в hash не входит. Смена языка отчёта меняет evaluationInputHash и исключает повторное использование результата другого языка. Он различает настройки оценки одного и того же решения; не зависит от времени или номера запуска. Полный snapshot с execution metadata сохраняется отдельно, его целостность не подменяется semanticContentHash.

[semantic-export.json](examples/semantic-export.json) проверяется схемой v1; [semantic-projection.canonical.json](examples/semantic-projection.canonical.json) фиксирует точные байты проекции. Для solution набор diagramIds — все диаграммы текущего снимка; добавление/удаление диаграммы меняет хеш общей оценки.

`documentRevision` меняется при любом сохранённом изменении. Для пометки «Оценка предыдущей версии решения» сравнивается semanticContentHash в той же области diagramIds. Перемещение объектов и повторный запуск не делают смысловую оценку устаревшей; изменение релевантного текста, порядка сообщений, требований или критериев приёмки делает. Новая версия рубрики/модели показывается как изменение настроек, отдельно от изменения решения. Недоступная/удалённая область прежнего запуска автоматически считается несовместимой с текущей подсветкой.

Валидация ссылок/типов выполняется до платного вызова. Структурно корректные, но незавершённые схемы можно оценивать с явно отмеченной неполнотой. Превышение лимита модели не разрешается скрытым обрезанием графа.
