# sysdes — работа по SDD

Статус: Baseline 1.0. Подтверждено по Q-01: Spec-Driven Development, Markdown + JSON Schema/OpenAPI в Git, без отдельного генератора.

## Принципы проекта

1. Спецификация содержит наблюдаемое поведение, инварианты и негативные сценарии до начала реализации.
2. Семантическая модель sysdes независима от renderer, SQLAlchemy и AI-провайдера.
3. Неизвестные требования/бизнес-показатели отмечаются явно; AI не превращает предположение в факт.
4. У каждого FR есть критерий проверки. Изменение поведения сопровождается изменением спецификации и контракта в том же наборе изменений.
5. Машинные схемы — источник истины формата; документированные инварианты дополняют то, что JSON Schema не выражает, например разрешение ссылок.
6. Личные данные и AI-ключи не попадают в другой аккаунт, bundle или логи.
7. Повтор и отказ сети рассматриваются для каждой сохраняющей/платной операции.
8. Начальный деплой — Docker Compose на одном хосте; сложность добавляется по конкретным требованиям или измерениям.
9. Технические SLI в MVP проверяются простыми локальными замерами в текущих редакторских сценариях. Product/UX analytics, кликстрим и collector отложены; готовая спецификация развития не является задачей их реализации.

## Цикл изменения

1. **Specify:** цель, роли, scope, FR, негативные сценарии, бизнес-критерии.
2. **Clarify:** закрыть вопросы, различить обязательное и предлагаемое; обновить decision log.
3. **Design:** выбрать вариант, определить model/API/AI contracts, риски и ADR.
4. **Baseline:** согласовать версию; выпустить полные JSON Schema и OpenAPI, проверить примеры.
5. **Plan:** разбить согласованный объём на вертикальные задачи с AC и зависимостями.
6. **Implement:** реализовать задачу в пределах контракта; новые требования возвращаются в Specify.
7. **Verify:** проверки модели, API/БД, browser flows, эксплуатация; отдельно benchmark AI.
8. **Review:** проверить трассировку FR → контракт → AC → результат; выпустить новую версию спецификации.

Минимальная единица SDD — законченный пользовательский сценарий, а не отдельный технический слой. Для каждой задачи нужны ссылки на FR/AC, затронутые версии контрактов и доказательство соответствия.

Первый сквозной срез после UX-проверки: вход → шаблон одного домена → изменение критерия приёмки и HLD-блока → сохранение → оценка через mock adapter → текстовый результат с версией. Реальные платные вызовы подключаются после корректности этого пути.

## Definition of Ready / Done

Ready для задачи: закрыты влияющие на неё Q, определены FR/AC, machine contract и ownership, негативные сценарии, размер/временной бюджет и схема отката при изменении данных.

Done для задачи: реализация соответствует согласованной версии, релевантные проверки выполнены с результатами, примеры валидны, нет молчаливых изменений поведения, обновлены ADR/спецификации и пользовательское описание.

Статус контракта: Draft → Reviewed → Accepted → Superseded. Несовместимое изменение schemaVersion/API требует явного решения и миграции; изменение prompt/rubric тоже версионируется.

В рабочем каталоге по запросу пользователя создан локальный Git-репозиторий с основной веткой main. Первоначальный пакет Draft 0.4 зафиксирован коммитом; последующие ответы опроса обновляют рабочую версию; реализация приложения остаётся отдельным этапом после согласования спецификаций.

Уточнение по 10C/11A/12A: этап сохранения/загрузки включает общий выбор аккаунта с отдельной ревизией и защитой черновиков других устройств (FR-26 / AC-45); ER соответствует логической модели с необязательными типами/индексами; регистрация открыта. Q-09/Q-10 закрыты ответами 13A/14A/15A: 10 запусков в сутки UTC, обязательные суточный/месячный денежные лимиты с резервом и операторский сброс пароля с обязательной сменой. Этап auth включает служебную команду и ограниченную сессию смены; этап AI — транзакционный учёт квот/резервов и сверку неизвестных исходов. Суммы лимитов заполняются владельцем перед включением AI.

Уточнение по 16A/18D/19A: в MVP входят экспорт JSON/PNG/SVG и удаление с подтверждением (FR-27/28, AC-51…54). Прототип редактора должен проверить экспорт смешанных объектов, шрифтов/подписей и независимость SVG от внешних ресурсов. Этап хранения включает атомарное удаление и защиту dirty-черновиков других устройств. Q-11 закрыт: лимит 1000 холстов на аккаунт, один сохранённый отчёт на каждый, без TTL. Этап хранения включает атомарный контроль количества/освобождение места; по 23A последний успешный результат любой из четырёх команд полностью заменяет отчёт и snapshot. Проверки FR-29 / AC-55…56.
