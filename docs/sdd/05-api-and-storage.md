# sysdes — API, хранение и безопасность

Статус: Baseline 1.0. [OpenAPI 3.1.1](contracts/openapi.json) содержит 31 операцию со встроенными схемами для автономной проверки. Runtime-схема FastAPI сверяется с этим контрактом; дополнительные инварианты — в [14-machine-contracts.md](14-machine-contracts.md).

Контракт охватывает общую оценку solution и диагностики hld/er/sequence. Баллы и чек-лист — в [evaluation-result-v2.schema.json](contracts/evaluation-result-v2.schema.json), вход — в [evaluation-input.schema.json](contracts/evaluation-input.schema.json). overallScore 1–5 не используется для новых баллов.

## HTTP

Префикс `/api/v1`; JSON UTF-8; одна origin для SPA/API; opaque IDs, не связанные с именем. В API термин `solutions` означает сохранённые холсты. Для структурных данных входа/выхода неизвестные поля отклоняются. Для доменных текстов разрешены обычные Unicode-строки, но не произвольный HTML.

Выбора модели, пользовательского ввода API-key и endpoint для произвольного proxy-запроса к AI нет. Модель в ответе оценки — фактически использованная server configuration. Удаление холстов и экспорт JSON/PNG/SVG входят в MVP по 18D/19A; экспорт Mermaid выполняется целиком на клиенте из локального снимка и не имеет endpoint.  Универсальное клонирование, пользовательский импорт и история восстановления revisions остаются кандидатами после MVP. Узкое действие «Сохранить конфликтующую копию» включено в FR-24 для предотвращения потери работы и описано отдельным endpoint.

Чтение каталогов разрешено авторизованным пользователям. Стартовые записи пишутся доверенными миграциями/операторской процедурой либо ролью admin через API; пользовательский путь записи — публикация собственного решения по D-45, проходящая те же проверки неизменяемости версий. Рубрику записи утверждает её владелец: право утвердить свою рубрику принадлежит автору публикации, а не только оператору, иначе собственная запись остаётся неоцениваемой до вмешательства извне. GUI каталога входит в MVP по FR-33: список с фильтрами домена, сложности и происхождения. Стартовое наполнение — восемь шаблонов; API и GUI выбора не ограничивают домен двумя шаблонами. Версия шаблона содержит локализации ru/en при стабильных ID и весах. Чтение каталога принимает locale=ru/en (по умолчанию ru); неподдерживаемое значение — 422. Создание холста принимает templateLocale=ru/en для копирования выбранного языкового варианта (по умолчанию ru); provenance сохраняет его вместе с версией. Импорт шаблонов из внешних форматов и произвольное создание шаблонов не входят в MVP API. Запись каталога хранит полный шаблон и разрешённые уровни раскрытия; в ответе карточки сервер отдаёт только раскрытую часть и никогда не присылает скрытые объекты, поэтому уровень раскрытия является контролем доступа, а не подсказкой отображения. Условие задания — требования, критерии приёмки и известные величины — раскрытием не управляется: это сама задача, а не ответ на неё, и карточка без условия оставляет читателя с одним заголовком. Оно же переносится в контекст созданного холста с новыми ID и ссылкой на исходные объекты записи, поэтому автор видит задание, пока рисует, и модель читает его вместе со схемой. Отдельная операция чтения записи целиком отдаёт весь документ шаблона: это не обход раскрытия, а другой режим работы с каталогом — изучение разобранного примера вместо решения задачи. Из этого же режима роль admin правит шаблон: редактирование включается явно, чтобы случайное движение мышью не переписало запись. Исправление сохраняется поверх шаблона (PUT версии, которую читали): запись сохраняет свою версию и остаётся в списке одной строкой — публикация каждой правки новой версией показывала запись дважды, и выбрать исправленную было нечем. Другой исход правки — «сохранить как» с новым именем (POST копии): получается отдельный шаблон с версии 1, исходный остаётся нетронутым, и веса переносятся с переписанной ссылкой на новую запись. Версия, из которой создан холст, остаётся адресуемой на чтение. Веса правкой поверх шаблона не меняются: холст закрепляет версию рубрики, под которой начат, и сохранённый отчёт оценён по ней, поэтому утверждение рубрики по-прежнему публикует новую версию. Наследование опущенных полей избавляет редактора от пересылки обеих локализаций ради исправления одной диаграммы и не даёт молча потерять утверждённую рубрику. Звёзды сервер считает как сумму уровня раскрытия и резерва сложности записи и не принимает это число от клиента. Публикация пользователя без утверждённой владельцем рубрики читается и фильтруется, но не принимается как источник оцениваемого задания.

В БД хранится каталог неизменяемых версий рубрик: пункты, веса, уровни, referenceScore и привязка к шаблону/общей рубрике Custom. Снимок оценки содержит применённую версию и её содержимое. Клиент не подменяет рубрику или веса в POST оценки. Рубрику можно закрепить и за собственным холстом, не публикуя его в каталог: автор учится по выбранным критериям, и требовать ради этого публикации было бы платой не за то. Закреплённая рубрика фиксируется конкретной утверждённой версией, поэтому её последующее изменение не переписывает уже полученные отчёты. Публикация новой рубрики не переписывает старые оценки. DDL/seed каталога остаются за пределами текущего опроса.

## Квота сохранённых холстов

Серверный настраиваемый лимит на аккаунт — 1000. Все persisted solutions учитываются одинаково, включая Custom и конфликтующие копии. Создание проверяет фактическое количество и занимает место атомарно с созданием ресурса; параллельные create/conflict-copy/delete сериализуются на строке владельца либо эквивалентном механизме БД. При 999 холстах из двух новых параллельных create проходит только один.

Повтор успешного Idempotency-Key возвращает прежний ресурс без проверки нового свободного места/выделения второго слота. Неуспешное создание не занимает место; DELETE освобождает место в той же транзакции. Save, экспорт и обновление отчёта остаются доступны при лимите. UI получает capacity.used/limit из списка; при создании авторитетна повторная серверная проверка, а не значение в браузере.

При уменьшении конфигурационного лимита ниже текущего количества данные сохраняются, создание блокируется до освобождения места. Текущая запись отчёта уникальна по solution_id; технические записи jobs без содержимого не считаются вторыми отчётами. История полных snapshots/results не хранится; по 23A последний проверенный результат любой команды атомарно заменяет отчёт и snapshot, включая смену evaluationType/locale. Ошибка старый отчёт не удаляет. Точный срок минимальных технических/финансовых метаданных — эксплуатационная настройка, без удаления незакрытых обязательств.

## Экспорт и удаление

Экспорт предлагается выполнять в браузере из единого локального snapshot после flush, без дополнительного API и обязательного save. JSON имеет отдельный versioned envelope с name/domain/provenance/document; контракт задан canvas-export.schema.json. PNG/SVG отображают всю область объектов и подписей. SVG должен быть самостоятельным изображением без script, обработчиков событий, произвольного HTML и внешних сетевых ресурсов; текст пользователя экранируется. Выбор библиотеки/способа рендеринга и ограничения размеров проверяются прототипом, не считаются уже решёнными.

DELETE проверяет владельца и If-Match в транзакции с блокировкой ресурса, согласованной с PUT и созданием evaluation. Queued/running job запрещает удаление до terminal state. Терминальный outcome_unknown допускает удаление текстового содержимого; provider/request ID, стоимость и резерв остаются в отдельном минимальном учёте для сверки. DELETE не каскадирует этот учёт и не освобождает резерв.

Если удаляемый холст выбран текущим, currentSolutionId становится null и selectionRevision увеличивается атомарно; иначе выбор не меняется. Удаляются документ, отчёты и входные snapshots. Локальные черновики других устройств не стираются принудительно. Поздний PUT/POST evaluation не воссоздаёт отсутствующий ресурс. Повтор DELETE отсутствующего ID даёт 404 без побочных эффектов. Записи идемпотентности для удалённых ресурсов сохраняют только необходимый маркер: повтор старого ключа не создаёт ресурс заново и не возвращает удалённое содержимое.

Потеря ответа DELETE разрешается GET/обновлением списка: 404 для ранее собственного ID подтверждает отсутствие ресурса; недоступная сеть оставляет исход неизвестным. UI не показывает успешное удаление до подтверждения. Сроки очистки backup и политика внешнего провайдера не определяются этим endpoint.

## Ошибки

Единый ответ `application/problem+json`: type, title, status, code, detail, correlationId; для валидации violations с путём поля и коротким сообщением. Stack trace, SQL, ключи и внутренние URL не возвращаются.

Различать `login_taken`, `invalid_credentials`, `revision_conflict`, `invalid_document`, `invalid_reference`, `input_too_large`, `quota_exceeded`, `budget_exceeded`, `ai_not_configured`, `password_change_required`, `ai_unavailable`, `invalid_result`, `deadline_exceeded`, `outcome_unknown`. Ошибка исполнения job хранится в job; GET job возвращает 200 с failed state, а не маскирует это как ошибку транспорта.

Недоступность чужого ID возвращает 404. Login uniqueness допускает сообщение о занятости логина согласно исходному FR; endpoint входа существование аккаунта не раскрывает.

## Конкурентность и идемпотентность

- Ресурс solution содержит монотонный revision. `If-Match: "17"` разрешает update, только если текущий revision = 17; обновление и increment выполняются атомарно.
- Ручное сохранение и автосохранение используют один PUT без отдельных endpoint/таблиц. Клиентский координатор допускает одну незавершённую запись холста, объединяет повторные ручные команды и не ставит минутные тики в очередь. UI остаётся интерактивным; локальный snapshot/generation определяет, какие правки подтверждены. Подробный контракт — [11-canvas-saving.md](11-canvas-saving.md).
- UI сохраняет base revision. После 412 доступны сохранение своей версии в новый холст или загрузка серверной версии с явным подтверждением потери локальных правок; автоматического merge нет.
- Conflict-copy валидирует локальный документ, владельца, неизменность домена и template provenance относительно исходного ресурса; затем создаёт новый canvasId и новые objectIds с полным переназначением ссылок. Старый холст не меняется. Исходный template version может быть снят с публикации, если он уже принадлежит исходному решению. Сбой создания копии оставляет локальный документ открытым.
- Повтор PUT после потерянного ответа не обязан вернуть 200. До следующего PUT получить ресурс и сравнить полные name + document, включая layout, с отправленным снимком; semanticContentHash для этого недостаточен. Совпадение подтверждает снимок и актуальный revision, но не новые локальные правки. Неизменившийся base revision допускает повтор; другой revision с отличающимся содержимым требует разрешения конфликта. При недоступном GET исход остаётся неизвестным, локальные данные сохраняются.
- Создание холста и evaluation требуют Idempotency-Key. Уникальность scoped по userId + operation + key, срок хранения принят 24 часа. Одинаковый key/body возвращает тот же ресурс; тот же key с другим body — 409.
- Создание evaluation атомарно проверяет текущий revision и владение, сохраняет snapshot и job. Внешний AI-вызов не выполняется внутри транзакции.
- Координатор объединяет подготовку снимка и POST evaluation в последовательную клиентскую операцию: следующий собственный PUT ждёт принятия job или завершения подготовки с ошибкой. Это не блокировка БД/редактора; после принятия job автосохранение продолжается независимо от AI. Конкурентная запись другой вкладки всё ещё может дать 409 при POST.
- Право worker на обработку закрепляется атомарно в БД. Долгая транзакция/блокировка строки на время HTTP запрещена.
- Защита от параллельных запусков на пользователя и резерв бюджета выполняются в БД одной транзакцией; in-memory semaphore ограничивает только работу процесса.

PostgreSQL допускает `FOR UPDATE SKIP LOCKED` для конкурентного чтения очередей; это возможный механизм claim. Он не заменяет состояния, deadline и правила восстановления. [SELECT / locking](https://www.postgresql.org/docs/current/sql-select.html).

## Общий текущий холст

По 10C сервер хранит один выбор на аккаунт. Предлагаемые GET/PUT выше используют отдельную selectionRevision: она не является revision документа. PUT проверяет владельца цели и меняет выбор атомарно; одинаковая уже выбранная цель не требует нового номера ревизии. Потерянный ответ разрешается GET, без слепого повторного переключения поверх более нового выбора. Клиент перед PUT подготавливает документ цели и разрешает собственные dirty/in-flight записи.

POST создания и conflict-copy создают ресурс; переключение на него выполняется отдельным условным PUT выбора после успешной подготовки. Если PUT выбора не удался, созданный ресурс доступен в списке; повторное создание не требуется. Обычный PUT документа, фоновый save и завершение AI никогда не меняют currentSolutionId. Сохранение прежнего своего документа допускается для восстановления черновика, не возвращая его в общий выбор. Не требуется блокировать аккаунт на время сетевого запроса другого устройства.

## Стандартное имя холста

При name=null сервер формирует solution-YYMMDD-NNN по времени UTC на момент создания. Счётчик отдельный на пользователя и дату UTC; начинается с 001, после 999 выдаёт 1000. Номер выделяется атомарно вместе с созданием; повтор с тем же Idempotency-Key возвращает прежний холст, в том числе после полуночи. Явное имя не расходует счётчик. Переименование не меняет ID и счётчик; имя не является глобальным идентификатором.

Не добавлять GIN ко всему JSONB без реальных запросов по его содержимому.

`solutions.domain_id` должен совпадать с semantic.domainId; домен ресурса — авторитетное значение, проверяемое при save. Template provenance в документе проверяется по каталогу при create и не может быть произвольно переписан клиентом при save. При прямом изменении document API нельзя сменить владельца/домен/происхождение.

Хранятся текущий документ и snapshots оценок. Полная история каждого перемещения/сохранения не нужна. Подтверждён лимит 1000 холстов на аккаунт и максимум один сохранённый отчёт на каждый, без TTL. Очистка не должна удалять template version, необходимую для актуального отчёта/холста. Удаление холста удаляет содержательный отчёт и его снимок, но не незакрытые финансовые обязательства.

## Аутентификация и права

Принято по 22A: собственные логин/пароль, Argon2id и opaque session cookie. Авторизация — проверка принадлежности ресурса на каждом API-методе. Ролей две: `user` и `admin`. Owner-based policy остаётся основой — почти всё, что делает пользователь, он делает со своим ресурсом; роль admin добавляет ровно одно право, редактирование записей каталога, и не заменяет проверку принадлежности там, где она уже работает. Отдельная RBAC-платформа для двух ролей не требуется. Роль выдаётся операторской командой и возвращается в public user.

- Login: принято `[A-Za-z0-9._-]{3,32}`; uniqueness по ASCII lowercase, отображение исходного регистра. Unicode-логины требуют отдельного правила нормализации.
- Password: принято 12–128 символов, без скрытого обрезания и обязательных классов символов. Проверка размера байтов дополнительно ограничивает стоимость запроса.
- Password hashing — Argon2id библиотекой; параметры калибруются на целевом сервере. Минимум OWASP на дату исследования: 19 MiB, t=2, p=1. Конкурентность проверки ограничена, чтобы регистрация не исчерпала RAM. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- Cookie: HttpOnly, Secure в production, SameSite=Lax, Path=/; новый session token после login; auth response `Cache-Control: no-store`.
- По 22A абсолютный срок обычной сессии семь суток (конфигурируется); logout отзывает текущую сессию. Выход из всех устройств — операторская процедура до отдельного UI.
- Mutating requests проверяют Origin и CSRF token; login/register защищены проверкой Origin и разрешённого Content-Type, поскольку сессии ещё нет. CORS для произвольных origin закрыт.
- Rate limit на регистрацию и вход по IP/логину; ответ 429 с Retry-After. Значения настраиваются и проверяются на отсутствие обхода через разные регистры логина.
- Секреты и тексты холстов не журналируются; audit фиксирует actor ID, действие, ресурс, исход и correlationId.

Родительское `AGENTS.md` вне репозитория содержит общее правило OAuth2/OIDC для внешних API. По ответу 22A принято уточнение для MVP: API является backend собственной SPA, регистрация и вход ограничены логином/паролем по заданию. Федерация, сторонние API-клиенты и отдельный IdP не включаются. Это проектное решение отмечено в ADR-003; при появлении интеграционных клиентов или корпоративного SSO правило OAuth2/OIDC применяется к этому новому интерфейсу. Login/password и OIDC в принципе совместимы; вопрос в дополнительной инфраструктуре, а не в невозможности сочетания.

## Операторский сброс пароля

Согласовано 15A. Оператор использует служебную команду на сервере, без публичного reset endpoint и административного GUI. Он проверяет владельца через доверенный внеприложенческий контакт; знание логина не подтверждает владение. Если подтвердить владельца нельзя, сброс не выполняется.

| Шаг | Действие и результат | Негативный сценарий |
|---|---|---|
| 1 | Оператор проверяет владельца и выбирает существующий user ID | Неизвестный ID или неподтверждённый владелец — без изменений |
| 2 | Команда создаёт случайный временный пароль, сохраняет только хеш, устанавливает must_change_password и срок действия; атомарно увеличивает credential_version и отзывает все сессии | Ошибка транзакции не оставляет частичный сброс; повторный сброс делает прежний временный пароль недействительным |
| 3 | Оператор передаёт временный пароль подтверждённому владельцу вне приложения | Пароль не передаётся в аргументах CLI и не пишется в application/audit logs; вывод секрета — только явный интерактивный канал оператора |
| 4 | Пользователь входит с временным паролем | Истёкший/неверный пароль — отказ; успешный вход даёт ограниченную сессию только для me, смены пароля и logout. Доступ к холстам/AI запрещён до смены |
| 5 | Пользователь задаёт новый пароль через change-password | Неверный текущий или невалидный новый пароль не снимает ограничение; новый не может совпасть с временным. Успех атомарно меняет хеш, снимает флаг, очищает срок, отзывает все прежние сессии и выдаёт новую полную |

По 22A настраиваемый срок временного пароля — 24 часа, ограниченной сессии — 15 минут и не позже истечения временного пароля. Эти стартовые значения приняты и войдут в baseline безопасности. Проверка credential_version на защищённых запросах не допускает использования сессии, созданной параллельно со сбросом по старому паролю; уже принятые операции не откатываются. Auth/me и logout остаются доступны в ограниченной сессии. Audit хранит только actor/user ID, факт и исход сброса без пароля. Открытые вкладки после отзыва сохраняют локальные черновики по действующим правилам и требуют повторного входа.

Квоты и бюджет согласованы в Q-09: 10 запусков за сутки UTC, общий счётчик для четырёх команд, обязательные суточный и месячный денежные лимиты. Резервирование, возврат квоты и сверка стоимости описаны в [04-ai-evaluation.md](04-ai-evaluation.md); их изменение и создание job выполняются транзакционно. Перезапуск приложения не обнуляет счётчики/резервы. Владелец задаёт суммы до включения AI, без них редактор работает с выключенной оценкой.

## Эксплуатация

- Liveness отделён от readiness. Потеря AI не отключает редактирование/сохранение; UI показывает недоступность оценки.
- Логи структурированы: correlationId/evaluationId, duration, state, errorCode, provider ID без секретов. Метрики: latency save, очередь, таймауты, invalid_result, outcome_unknown, расход/резерв, память.
- В MVP User-centric Latency проверяется локально по [09-technical-sli.md](09-technical-sli.md). Product/UX analytics, collector, telemetry endpoints/таблицы и их отчётность не включены в текущий API/DDL. Возможное развитие описано в 10; стандартные серверные логи/health checks не расширяются до кликстрима.
- Backup PostgreSQL ежедневно на отдельный носитель; принятые RPO 24 часа и RTO 2 часа проверяются восстановлением. Docker volume сам по себе не backup.
- Обновление БД по expand/contract; destructive migration требует отдельного плана. Rollback приложения разрешён только при совместимости схемы документа и БД.
- Один хост остаётся точкой отказа. High availability не входит в заданную первую версию.

Стабильные коды: 403 password_change_required для доступа ограниченной сессии к холстам/AI; 409 canvas_limit_exceeded / evaluation_in_progress / revision_conflict, 429 quota_exceeded / budget_exceeded, 503 ai_not_configured. Недоступность вытесненного результата — resultAvailable=false, result=null при сохранённых метаданных job. Idempotency повторяет принятие job без нового вызова; при уже удалённом ресурсе возвращается 410 resource_deleted без содержимого и повторного создания.
