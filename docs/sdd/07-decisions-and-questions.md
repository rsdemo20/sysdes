## Архитектурные решения (ADR)

### ADR-001. Стек и единица развёртывания

Статус: Accepted — ответ 20A. Контекст: личный редактор, 1–100 DAU, Docker Compose, один внешний AI-вызов на запуск.

Решение: React/TypeScript/Vite, FastAPI, PostgreSQL; модульный монолит с встроенным async worker. Варианты Go и TypeScript/Fastify рассмотрены в 02, но не соответствуют текущему предпочтению backend.

Плюсы: компактная эксплуатационная схема, нет отдельного брокера, документ и job фиксируются транзакционно. Цена: app и worker делят процесс; CPU-операции и конкуренцию нужно ограничивать. Выделение worker возможно через сохранённую таблицу заданий. Смена языка backend — средняя стоимость при независимых контрактах.

Пересмотр: измеренный RSS не помещается в целевой бюджет; AI влияет на save latency; требуется больше одного app-процесса или очередь регулярно исчерпывает пятисекундный бюджет.

### ADR-002. Независимая семантика и React Flow

Статус: Accepted — ответ 21A. Решение: versioned CanvasDocument с semantic/layout; React Flow — адаптер отображения; экспорт AI — канонический типизированный JSON.

Альтернативы: Excalidraw, tldraw, собственный Canvas engine. Причина выбора — управляемые типы объектов/связей, ER-данные и адресуемые замечания. Цена — собственная логика Sequence, привязанных полей и undo/redo. Смена renderer средняя при сохранении независимой модели; после сцепления с внутренними nodes/edges стала бы высокой.

Первый эксперимент после согласования: смешанный холст с HLD-блоком, ER-полями, двумя участниками Sequence и тремя сообщениями; перетаскивание/resize подписей, reorder, save/load. Пересмотреть renderer при провале AC-04/05/06; не менять библиотеку на основании одного статического скриншота.

Уточнение Input Isolation: предлагается локальный useState в компоненте поля и адресный text.commit, дополненные мемоизацией/узкими подписками. Граница blur / Enter дополнена flush перед сохранением/оценкой, чтобы активный текст попадал в snapshot. Dirty-generation хранится в ref координатора, не вызывает обновление графа на каждую клавишу. Альтернативы и проверяемое поведение — в [12-input-isolation.md](12-input-isolation.md); производительность ещё не измерена.

### ADR-003. Identity для собственной SPA

Статус: Accepted — ответ 22A. Решение: локальные логин/пароль, Argon2id, серверная сессия в cookie, owner-based authorization. Альтернатива: отдельный OIDC provider с локальными учётными записями.

Причина: исходный минимальный сценарий регистрации и малое окружение. Цена: lifecycle паролей/сессий реализуется и проверяется в приложении, самостоятельного восстановления по email нет. Вопрос общего требования OAuth2/OIDC из родительского AGENTS.md зафиксирован в 05; OIDC не несовместим с логином/паролем, но отдельная инфраструктура пока не обоснована продуктом.

Пересмотр: корпоративное SSO, внешние API-клиенты, MFA, несколько продуктов с общей учётной записью. Смена identity — средняя стоимость при стабильных user IDs.

### ADR-004. Оценка по снимку и структурированный результат

По Q-11 сохраняется максимум один отчёт на холст без TTL. По 23A последний успешный результат любой команды заменяет прежний отчёт целиком вместе со снимком. Истории содержательных результатов нет; ошибка нового запуска оставляет прежний отчёт.

Продуктовые решения подтверждены в Q-13: общий балл плюс три отдельные диагностики, утверждённая владельцем рубрика, ориентир 1500 и процент не выше 100. Строгий структурированный ответ принят по 24A; хранение/замена — по 23A. Полные схемы входят в baseline 1.0.

Статус: Accepted — ответы 23A/24A. Решение: immutable evaluation input, версия рубрики/шаблона/модели, строгий JSON output, проверенные objectRefs и серверный расчёт баллов; текст в нижней панели, последний успешный отчёт заменяет прежний.

Альтернатива: отправлять сериализованный рисунок и сохранять только произвольный текст. Она проще в начале, но не определяет, к чему относится замечание и какой версии решения соответствует результат. Другая альтернатива — оценка screenshot; не обеспечивает необходимой полноты скрытых атрибутов и бизнес-критериев.

Цена: строгая модель, валидатор ссылок, хранение snapshot. UI подсветки можно отложить. Пересмотр: выбранная модель систематически не выдерживает structured output; сначала сменить поддерживаемую модель/формат, затем расширять pipeline на основании benchmark.

### ADR-006. Синхронизация выбора аккаунта

Статус: Accepted — ответ 25A. Общий currentSolutionId и selectionRevision в БД, условный PUT; polling каждые 5 секунд только в видимой вкладке, дополнительно при входе/фокусе/возврате сети. Альтернатива SSE отклонена для MVP ради меньшего количества механизмов. Старые dirty-черновики защищаются координатором; офлайн/скрытые вкладки догоняют состояние при возврате. Пересмотр: измеренная стоимость polling или требование меньшей задержки уведомления.

## Архитектурная проверка

Выполнена независимая проверка предложения в роли ARCH-ADVERSARY. Учтены замечания: отдельный контекст задачи, типизированные модели схем, snapshot и происхождение шаблона, защита от повторных платных вызовов, bounded queue, разделение auth-сессии и холста, ссылки для будущей подсветки.

Не принято усложнение до микросервисов или отдельного брокера: конкретного требования к их независимому отказу/масштабированию нет. Проектные допущения не представлены как дефекты существующего кода.

```text
VALIDATION | agents: [ARCH-PRIMARY, ARCH-ADVERSARY, ARCH-SYNTH] | agreement: high | unresolved: 0 | ready: no
```

PRIMARY/SYNTH выполнены основным агентом, ADVERSARY — отдельным агентом в первоначальной проверке Draft. Эта строка сохраняет историю архитектурной проверки, а не объявляет новую независимую проверку baseline. Все Q-01–Q-13 и ответы 24A/25A/26A зафиксированы. Контракты проверены локальным валидатором; ready=no здесь означает, что прототип и приёмка приложения ещё не выполнены. Пакет готов для начала задач реализации, а не для выпуска продукта.
