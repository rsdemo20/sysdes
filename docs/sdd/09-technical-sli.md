# sysdes — технические SLI и приёмка MVP

Статус: Baseline 1.0. Приоритет пользователя: **измерения не должны заметно замедлять разработку приложения**. Для MVP достаточно проверять техническую отзывчивость в уже предусмотренных сценариях редактора. Продуктовая аналитика и кликстрим перенесены в [следующие итерации](10-observability-next.md).

## Объём MVP

- Профилировщик браузера для drag/pan/zoom и задержек отрисовки.
- Небольшие локальные замеры через Performance marks/measures только там, где штатного профилировщика недостаточно. Допустим временный helper в dev/test; отдельная измерительная библиотека не требуется.
- Результат — короткий протокол проверки с размером сцены, браузером, условиями, durations и обнаруженными задержками. Его можно заполнить вручную.
- В первой версии не разрабатываются collector сессий, поток продуктовых событий, корреляция кликов/Undo, telemetry API, таблицы аналитики, dashboard и интеграция с внешней аналитической платформой.
- Технические проверки входят в существующую приёмку редактора. Выделять отдельный этап разработки аналитики или ждать статистики реальных пользователей для выпуска MVP не требуется.

## Метрики и цели

| ID | Что измерять сейчас | Технический порог | Полевой SLO после появления наблюдаемости |
|---|---|---|---|
| TECH-01 | Плавность drag, pan и zoom: frame intervals, доля медленных активных секунд, длинные gaps | Цель 60 FPS; предложено <=5% медленных активных секунд в контрольном прогоне, без stalls >100 ms при ожидающем обновлении | >94% подходящих сессий плавные; внутри-сессионное условие и допуск определяются в 10 |
| TECH-02 | От исходного input до видимого локального текста или результата конкретной команды; пути измеряются отдельно | <100 ms для ввода символа и для link.create, node.create, move/resize commit, text.commit, delete, undo/redo | Предложено >=99% операций каждого типа <100 ms |
| TECH-03 | Открытие выбранной схемы до готового первоначального viewport и интерактивности | <3 s, включая сеть, получение/разбор документа и renderer | Предложено >=95% первых загрузок <3 s, cold/warm отдельно |
| TECH-04 | Длинные задачи основного потока и их связь с задержкой | Диагностика в профилировщике; отдельный SLO не задаётся | При необходимости измерять долю blocking time |
| TECH-05 | От кнопки «Сохранить» / Ctrl+S / Cmd+S до видимого подтверждения ручной записи | Предложено <1 s при нормальной сети, включая ожидание уже идущего save | Предложено >=99% ручных сохранений <1 s; автоматические попытки учитывать отдельно |

Проценты по реальным сессиям/действиям — целевые определения для развития, **не выполненные и не обязательные для подтверждения перед первым выпуском**. Несколько контрольных прогонов не доказывают достижение полевого SLO. Приёмка MVP проверяет конкретные воспроизводимые операции и отсутствие наблюдаемого jank.

## Как измерять без отдельного аналитического контура

### Плавность

1. Взять фиксированную сцену: 150 блоков, 250 связей, 100 подписей и 40 сообщений Sequence; viewport 1440×900, монитор 60 Hz. Записать браузер и CPU устройства.
2. Выполнить drag, pan, zoom примерно по 30 секунд; предложено по три коротких прогона каждого сценария. Не включать hidden/idle-время и ручное чтение описания задачи в render interval.
3. Посмотреть Frames/main-thread trace и визуальное движение. Длинное ожидание обновления не вычитать из замера как «неактивность».
4. Если удобнее использовать локальный rAF helper, считать его **оценкой возможностей обновления**, а не доказательством реально показанных кадров. Живой rAF при замершем renderer не означает плавность.
5. При подсчёте секундных rAF-окон сохранять raw долю FPS <60. Допуск одного callback на границу окна предложен отдельно: 59 callbacks не считаются slow только для tolerant-расчёта. Такой допуск не доказывает буквальные 60 FPS; в протоколе указываются и метод, и допуск.

60 Hz даёт около 16,67 ms на кадр. rAF вызывается перед обновлением кадра, зависит от refresh rate и обычно приостанавливается в hidden tabs. Эти ограничения учитываются при чтении профиля. [Rendering performance](https://web.dev/articles/rendering-performance), [requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame).

### Action Latency

- Для создания связи старт — timestamp drop/подтверждения целевого порта; выбор порта пользователем не является технической задержкой.
- Для create/delete/Undo — timestamp запускающего click/keyboard event. Для move/resize commit — финальный pointerup; плавность самого движения проверяется отдельно.
- Для текста отдельные пути: input → видимое изменение локального поля и blur / Enter → результат text.commit в графе. Нельзя скрывать input lag, измеряя только commit после завершения набора; время размышления до blur или выбора IME-кандидата не является задержкой системы.
- Конец — изменение конкретной команды видно и доступно взаимодействию. Запись нового React state сама по себе не является завершением отрисовки.
- Замер от начала JS-handler пропускает задержку в очереди ввода. Для локальных marks использовать исходный event timestamp в общей монотонной шкале, а в профилировщике смотреть input → processing → rendering.
- При async renderer допустим небольшой dev/test probe, связанный с commit команды. Два rAF после commit дают лишь консервативный visual-ready proxy; при пограничных результатах уточнять реальным trace, а не строить универсальный paint detector.
- Предложено пять повторений каждого критического пути. Результаты приводятся по операциям; быстрые выделения не скрывают медленное соединение. 99,9 ms меньше 100, ровно 100 ms порог не проходит.

Event Timing/INP — дополнительные browser diagnostics. Continuous pointermove/wheel/drag не покрываются Event Timing, а его пороговые записи не дают счётчик всех быстрых действий. Поэтому отдельный расчёт INP/collector не требуется для MVP. [Event Timing — рабочая спецификация W3C](https://www.w3.org/TR/event-timing/), [User Timing](https://www.w3.org/TR/user-timing/).

Input Isolation проверяется по [12-input-isolation.md](12-input-isolation.md): короткий быстрый набор и вставка в название/описание, включая активный auto PUT. React Profiler показывает область перерисовок, Performance trace — отклик ввода; отсутствие лишних renders само по себе не доказывает <100 ms. Глобальный граф не обновляется на каждый символ, commit/flush проверяется отдельно. Новые runtime-события и продуктовая аналитика не требуются.

### Загрузка схемы и сохранение

`canvas_ready`: данные валидны, видимые узлы и связи размещены, необходимые для размеров шрифты готовы, controls работают и результат нарисован. Loading skeleton и ответ API без схемы не считаются готовностью.

Для автоматического cold-open существующего холста с действующей auth-сессией старт — начало navigation; для явного открытия — подтверждающий input. Ожидание пароля/выбора домена не включается. Cold-open и переключение между уже работающими холстами проверяются отдельно. Предложено по пять загрузок каждого проверяемого пути. 2 999 ms проходит, 3 000 ms не проходит; ошибка не превращается в «быструю загрузку».

FMP/TTI не используются как название собственного события готовности: они удалены из соответствующих проверок Lighthouse. LCP/FCP можно смотреть для оболочки SPA, но они не задают готовность выбранной схемы. [FMP](https://developer.chrome.com/docs/lighthouse/performance/first-meaningful-paint), [TTI](https://developer.chrome.com/docs/lighthouse/performance/interactive).

Подтверждение ручного сохранения измеряется end-to-end: input → ожидание координатора, если есть → сеть → транзакция БД → ответ → видимое подтверждение снимка. При новых правках после снимка корректен статус «Версия сохранена; есть новые изменения», а не «Все изменения сохранены». Ручное действие на clean-холсте без PUT проверяется как отдельный no-op и не улучшает статистику записей. Ошибки и 412 проверяются отдельно; быстрый отказ не является успешным save. Серверный p95 в NFR-03 остаётся отдельным бюджетом, не заменяет пользовательский отклик.

Для автосохранения проверяется функциональное расписание: один тик через 60 секунд после подтверждения/открытия, запрос только при dirty, без сброса таймера на каждой правке. Минутное ожидание не смешивается с latency ручной записи. Непрерывное редактирование и фоновая сериализация/PUT входят в короткий контроль плавности и Action Latency на стандартной сцене; оба режима должны оставлять редактор доступным. Ограничения hidden tabs и негативные сценарии описаны в [11-canvas-saving.md](11-canvas-saving.md). Новый полевой SLO, кликстрим или collector для этих проверок не требуется.

## Приёмка и границы затрат

- В контрольных прогонах применять технические пороги таблицы, записывать отклонения и исправлять воспроизводимые задержки критических действий. Это малая лабораторная выборка, не статистика всех пользователей.
- Нестабильный результат перепроверяется в тех же условиях. Перегруженный общий CI runner не используется как единственное доказательство медленного renderer.
- Простейшего профиля/локального замера достаточно; автоматизировать его только если это использует уже существующий тестовый контур и заметно сокращает повторяемую работу. Для первого выпуска не создавать универсальный метрический SDK.
- Стандартные сцену, версию приложения, браузер, cache/network conditions и измерительный метод записывать рядом с результатом. Результаты разных методов нельзя молча смешивать.
- Встроенные dev/test helpers не отправляют события и пользовательские данные по сети; можно отключать их в production. Обычные серверные health checks/логи сохраняются в ранее согласованном объёме.
- Задачи и проверки MVP: AC-23…25 в [06-acceptance.md](06-acceptance.md). Product/UX SLI и полноценный полевой сбор — только документированный backlog в 10.

## Что отложено

В будущих итерациях можно измерять: долю микро-отмен за <=5 s (цель >90% действий без них), длительное удержание drag, клики на стандартный task pattern, успешность жестов подключения и настоящую первую попытку в размеченной задаче (>87%), task completion. Undo и длительный drag остаются поведенческими индикаторами с несколькими возможными причинами, а не автоматической оценкой удобства.

Формулы, события, coverage, цензурирование и варианты хранения сохранены в [10-observability-next.md](10-observability-next.md). Наличие этой спецификации не означает включение аналитики в текущий план реализации.
